# Building a chrischall fleet MCP

The fleet is ~50 sibling MCP servers under `~/git/*-mcp`, all on the same skeleton and sharing `@chrischall/mcp-utils` (generic scaffolding), `@fetchproxy/server` (browser-bridge HTTP for sites without an API), and `@chrischall/realty-core` (realty math). Build new ones the same way; don't reinvent the glue.

Canonical examples to copy from: **splitwise-mcp** (bearer/direct-API archetype), **artsonia-mcp** (cookie-session / username+password archetype), **redfin-mcp** / **zillow-mcp** (fetchproxy archetype), **musicbrainz-mcp** (rate-limited public API — no-auth reads + OAuth-grant writes).

## Deliverable: fpx skill first, full MCP only on request

**Default to a lightweight shell-out skill, not a full MCP — always produce it, even when a full MCP is also requested. Its usual tool is `fpx`; use `curl`/node-fetch when the service is reachable server-side (see below).** `@fetchproxy/cli` (binary `fpx`) wraps the same browser bridge the fetchproxy archetype uses as a standalone one-shot CLI: point it at a URL or GraphQL endpoint and it fetches through the user's signed-in tab, no MCP process to run. For most "give me access to `<site>`'s data" asks, a shell-out skill is the whole job. **Match the tool to reachability:** use `fpx` only for the fetchproxy cases — bot-walled sites, or where the only credential is the live browser session — because every `fpx` verb routes through the signed-in tab. For anything reachable server-side (a public or bearer/token API), the skill shells out to plain `curl`/node-fetch with the key in a header — no bridge, no extension, no signed-in tab; routing a public endpoint through the tab buys nothing. Same lightweight skill tier either way; `fpx` is just the tool for the walled ones. (tripadvisor's Terra API = a `curl` skill; its no-key public-page fallback = the `fpx` bridge.)

Decide this BEFORE touching the skeleton or picking an archetype:

- **Not dictated** (user said "add `<site>`" / "I want `<site>` data" / "integrate `<site>`"): build the fpx skill, then **ASK** whether they also want a full MCP — say it's a much larger build (typed tools, normalization, tests, packaging, registry/plugin/CI) and most asks don't need it. Don't start the MCP until they say yes.
- **Full MCP dictated** ("build me a `<site>`-mcp", "make the MCP server"): **CONFIRM** before the full build — "that's the full server (~a day of build + release wiring); the fpx skill alone may be enough — want both, or just the skill?" — and **still ship the fpx skill too**, so they get both. The fpx skill is never skipped.
- **fpx skill dictated / "just a skill" / "without the MCP"**: do only the skill.

A full MCP earns its keep only when at least one of these is true — otherwise stop at the skill: **reachable from claude.ai / a phone / any client that isn't Claude Code on the box with the CLI** (a shell-out skill runs only where its `fpx`/`curl` binary lives — this is the single biggest reason to build the server, and the one a skill fundamentally can't cover; to actually DELIVER that reach, register it on **mcp-host** — see §*Hosting on mcp-host* — which needs no repo changes when the auth is serverless-safe, and is impossible for browser-bridge repos); typed/validated tools an agent calls without shelling out; normalized records + a library surface (e.g. realty-meta consumers); confirm-gated writes; a first-class healthcheck; distribution through the MCP registry / plugin marketplace. If none apply, the skill is the finished deliverable.

### Authoring the fpx skill

`@fetchproxy/cli` — install `npm i -g @fetchproxy/cli`; the user also needs the **Transporter** extension (same one the fleet's bridge uses). Model: one **profile** per service (`fpx profile add <name> --domain <apex>`), its own identity `fpx-<name>`, paired once (`fpx pair -p <name>` → approve the 6-digit code in Transporter; the trust persists across invocations). Verbs: `get` / `post-json` / `request` (fetch), `cookies` / `local-storage` / `session-storage` / `indexeddb` / `session` (reads), plus `health` / `pair`. `fpx profile declare <name> --cookie k --capture-header name@host` widens scope and forces a re-pair. **Output contract: stdout = data only** (pipe to `jq`), stderr = pair codes / status; fetch-verb exit codes `2` bridge down, `3` bot wall, `4` upstream non-2xx.

Author it with the `skill-creator` skill: a lean `SKILL.md` (one-time profile-add + pair; the core call pattern; any resolve-first rule; the exit codes) plus a `references/` file of ready-to-run request bodies with `jq` recipes. **Verify every request shape live before baking it in** (same rule as coding an MCP endpoint — capture the real request, don't guess). Ship it where the service's skills live: `<repo>/skills/<name>-fpx/` in a fleet repo (auto-discovered via `plugin.json` `"skills": "./skills/"`, and already covered by the package `files`), or a standalone skill dir otherwise. **Canonical example: `hemnet-mcp/skills/hemnet-fpx`** — anonymous GraphQL through the bridge, its `references/graphql-queries.md` carrying the live-verified query bodies.

**Authoring gotchas (from the 2026-07-13 fleet-wide build of 25 access skills):**

- **Pick the tool from the MCP's `client.ts`, not its archetype.** A repo that *depends* on `@fetchproxy/server` may bridge only ONE call (the auth/token mint) and curl everything else — resy's `api.resy.com` isn't bot-walled, so its skill is curl + a one-time `fpx post-json` token bootstrap, not full fpx. Read the client before committing to fpx vs curl vs hybrid.
- **When an MCP already exists, derive from it — don't re-capture.** Its `src/client.ts` / `src/tools/*.ts` / `docs/<SVC>-API.md` ARE the live-verified shapes; transcribe them (the "capture live" rule is for net-new services with no MCP). For HTML-parse-heavy sites, reuse the MCP's own parser via `node --input-type=module -e "import {parseX} from '<repo>/dist/parse.js'; …" | jq` rather than re-deriving brittle CSS selectors (artsonia).
- **SSR JS-object stores need an extractor, not `jq`.** Sites that embed an entity-encoded / bare-`undefined` JS-object store (`__NEXT_DATA__`, `$REDUX_STATE`, `window.__store__`, a global assign) can't be read by `jq` — a bare `window.x = {…}` assignment isn't even a script tag, so there's no regex that finds its end. **In an MCP, import `@chrischall/mcp-utils`'s `scrape` module** (`extractJsonAfterMarker` / `extractJsonLdBlocks` / `matchBalanced`) rather than writing your own — thumbtack-mcp hand-rolled a `parse.ts` and then deleted it for the library version. A standalone *skill* still needs a dependency-free `.mjs` in `references/` (no node_modules), so port the same logic there and verify it against real captured bytes before baking the recipes (musescore/tock/compass/zillow/thumbtack).
- **React Server Component flight rows: long strings are NOT JSON.** A Next.js **App Router** site (no `__NEXT_DATA__`, a `self.__next_f.push([1,"…"])` sequence instead) delivers records as flight rows `<hexid>:<json>`, recovered by concatenating the JS-string-escaped chunks — a record can straddle a chunk boundary, so concatenate before parsing. Two things a first-pass parser gets wrong: values are **deduplicated behind `"$<rowid>"` references that CHAIN** (`b5:["$b6"]`), and a long string is its own row in the form **`<id>:T<hexByteLength>,<raw text>`** — not JSON, length in **UTF-8 bytes not characters**, and it **may contain newlines**, so a line-splitting row parser silently misses it and leaves the field holding a literal `"$b6"` that reads like content. Also: `"$undefined"` means undefined, `"$$x"` is an escaped literal `"$x"`, a row referenced but never sent keeps its token (treat `^\$[0-9a-f]+$` as MISSING, don't emit it), and the payload is HTML-escaped (`Angie&#39;s`, `&amp;`). Verified on angi-mcp: 4 of 50 review bodies arrived as text chunks, longest 1,136 chars. A synthetic fixture cannot show this — only real bytes can.
- **Know fpx's verbs — check `fpx` with no args rather than trusting this list.** As of **CLI 2.1.0** it does `get`/`post-json`/`request` + cookie/localStorage/sessionStorage/indexedDb/`session` reads + `health`/`pair`/`trust`, **plus `dom <name…>` and `download <url>`** — the two verbs earlier fleet notes said were missing. They are declared as scopes (`--dom-selector handle=css`, `--allow-download`), so they must be in the profile BEFORE the first pairing like any other capability. This means the old "an fpx skill can only *resolve* a download URL, never fetch it" limit (easytable Turnstile, musescore scores, alltrails GPX) is worth **re-testing** before documenting it as a limit. `--via-tab <url>` relays a request through a tab on another declared host — the way to reach an API host that serves no page of its own.
- **`fpx health` cannot see another fpx process's bridge.** It spawns its OWN server instance, so it reports `role: null, lastExtensionMessageAt: null` even while a concurrent `fpx get` holds a live extension connection — which reads exactly like "the extension never connected" and invites a wrong diagnosis. To check a real in-flight request use `lsof -nP -iTCP:37149` **during** it: an `ESTABLISHED` line owned by Chrome means the bridge is fine and you are simply waiting on the pair approval.
- **EXECUTE the helper you ship, under bash AND zsh.** The "verify request shapes live" rule covers the *requests*; it does not cover the shell functions wrapping them, and those ship broken just as easily. kiaaccess shipped a `kia_headers`/`kia_curl` pair that was never run: it computed the GMT offset with `$(( $(date +%z | cut -c1-3) ))`, which dies under **bash** for `-08`/`+09` (leading-zero numerals parse as octal) — US Pacific in winter, Alaska, Japan, Korea, China. It worked for the author because the local timezone was `-04` **and the shell was zsh**, which has no such rule. Use `10#` to force base 10, prefer an array over a `sed`-built argument list, and actually source the block and drive one real authenticated read through it before committing. Also: **give the skill its OWN state file.** That same skill wrote `{rmtoken, deviceId}` to `~/.<svc>-mcp/session.json` — the MCP server's own store path, a different schema keyed by account — corrupting the server's session and forcing it back through MFA.
- **Pipe the helper into something that exits early, too.** Running it is not enough: `node references/x.mjs … | jq length` or `| head` closes stdout before the write finishes, and an unhandled **EPIPE** dumps a Node stack trace over the results. Any shipped `.mjs` that writes to stdout needs `process.stdout.on('error', e => { if (e.code === 'EPIPE') process.exit(0); throw e; })`. Caught only by actually running the documented pipelines (angi-mcp).
- **Two packaging checks.** (1) `package.json` `files` must include `"skills"` — many repos list only `dist`/`SKILL.md`, so a new skill silently wouldn't ship on npm. (2) `.claude-plugin/plugin.json` `"skills"`: canonical is `"./skills/"` (hemnet); if it points at `"./SKILL.md"` **and a root `./SKILL.md` exists**, LEAVE it (the skill still ships on npm but isn't plugin-auto-discovered until a separate root-skill migration) — repoint to `"./skills/"` only when the pointer is broken (no root skill to displace). Never move a root `SKILL.md` as a side effect.
- **Declare ALL fpx scopes BEFORE the first pairing — a later `profile declare` can't re-pair.** Widening scope after the initial approval (`fpx profile declare <name> --cookie k`) leaves fetch verbs working on the OLD grant while the new capability errors `capability "read_cookies" not granted`, and the `fpx pair` verb itself fails `no tab matching https://<apex>/ — extension/server version mismatch` even with a matching tab open (observed fpx CLI 1.4.0, 2026-07-30 eventbrite build). Recovery: `fpx profile remove` + re-add with full scope declared up front + trigger any fetch verb to surface a FRESH pair code (the pair verb is not needed — the first-ever pairing also completes via a plain `fpx get`). So decide cookie/header scopes (CSRF cookie!) before asking the user to approve anything, or you'll ask them twice.
- **Django-CSRF'd site POSTs through the bridge: send `X-CSRFToken` = the `csrftoken` cookie.** GETs are exempt; the POST needs the header, the cookie is JS-readable (not HttpOnly), and the page may embed NO `csrfmiddlewaretoken` anywhere (eventbrite's signed-in pages carry zero `csrf` strings — the JS reads the cookie directly), so `fpx cookies csrftoken` is the only scriptable source → the profile needs the cookie scope from day one (see above). Also send `X-Requested-With: XMLHttpRequest` alongside — capture showed the site always pairs them.

## Skeleton

```
src/
  index.ts        # bootstrap — runMcp({ name, version, banner, deps, tools })
  client.ts       # API client (reads creds, talks to the service)
  tools/<area>.ts # registerXxxTools(server, deps) → server.registerTool(...)
tests/            # vitest; no real network (mock fetch / the bridge)
  version-sync.test.ts   # versionSyncTest from @chrischall/mcp-utils/test
SKILL.md, manifest.json, server.json, .mcp.json, .claude-plugin/  # packaging
mint.yaml         # how this MCP wants to be HOSTED (mcp-host reads it; see below)
.github/workflows/   # ci, release-please / tag-and-bump, pr-auto-review, auto-merge
```

Each `tools/*.ts` exports `registerXxxTools(server, deps)` that calls `server.registerTool(name, { description, annotations, inputSchema }, handler)` (high-level `McpServer` API with zod). `index.ts` only wires them.

**Which healthcheck — and the classification trap.** Two factories, and the
choice follows how the MCP actually reaches its upstream:

- **Every request rides the browser bridge** → `registerBridgeHealthcheckTool`
  (`/fetchproxy`). Reports bridge role/port, whether the extension answered,
  and a probe round-trip. alltrails, etix, opentable.
- **Anything else** → `registerCredentialHealthcheckTool` (`/healthcheck`).
  That includes OAuth and API-key MCPs *and* the fetchproxy ones that only
  BOOTSTRAP a credential and then talk to an API directly.

Do NOT classify by imports. `createFetchproxyTransport` in a repo does not mean
the bridge is on the request path: resy constructs one EPHEMERALLY inside
`mintTokenViaFetchproxy()` — start, one `postJson` to mint a token, close — and
every call after that is a plain API request. Read where the transport is
HELD: a persistent bridge lives on the client for the process's life; a
bootstrap one is created and closed inside a function. Of ten repos audited
this way, one was a persistent bridge and nine were credential-shaped; the
import list suggested seven.

Three rules the nine consumers converged on, each of which was a real bug first:
- the probe is SKIPPED when no credential resolved — probing without one
  returns 401, which reads as "rejected" and sends people to re-authenticate a
  credential that does not exist;
- `resolveCredential` returns a SOURCE LABEL and non-secret detail, never the
  value — the result is what people paste into a chat when something is broken;
- run the resolver the REAL tools use, not a re-derivation. splitwise's
  re-derived copy diverged on `apiKey: ''` (truthiness vs `??`) and named a
  source the client had never consulted.

**Library→migrate discipline:** when you add a helper to mcp-utils, also migrate the hand-rolled consumers in the same wave — don't leave the loop half-finished (that's how `runWithDeadline`/`mapLimit`/the session registries drifted into N copies). Building a shared helper that no repo adopts is half a job.

## Bootstrap (index.ts) — both archetypes

```ts
#!/usr/bin/env node
import { runMcp } from '@chrischall/mcp-utils';
import { FooClient } from './client.js';
import { registerThingTools } from './tools/thing.js';

// Build the client in the CALLER so the deferred-config-error pattern holds:
// the server still boots (and answers the host's install-time tools/list probe)
// when creds are absent — the error surfaces on the first tool call instead.
const client = new FooClient();

await runMcp({
  name: 'foo-mcp',
  version: '1.0.0', // x-release-please-version
  banner: '[foo-mcp] This project was developed and is maintained by AI. Use at your own discretion.',
  deps: client,
  tools: [registerThingTools],
});
```

**Deferred-config-error pattern** (do this in `client.ts`): the constructor reads creds via `readEnvVar`; if missing, store a `configError` instead of throwing, and re-throw it from a `requireKey()` called at request time. Lets the server start without creds. **It can be PARTIAL:** if reads need no creds but writes do (the rate-limited-public-API archetype), defer only the write-side `configError` — reads always boot, the error surfaces on the first write.

## Archetypes

**FIRST, before any capture work: send ONE probe and find out whether the API already accepts you as a client.** A 30-second `curl` that decides the whole archetype. Take the endpoint + header constants from an open-source client (Home Assistant integrations, `*-api` PyPI packages) or a doc, POST a **deliberately invalid credential**, and read the error:

- *"invalid email or password"* → **your client identity was ACCEPTED.** The app key / `appversion` / secret header / User-Agent are all current; only the password was wrong. The service is reachable server-side and needs no capture at all.
- *"missing mandatory header"* / *"unsupported app version"* / a bot-wall interstitial → identity rejected. Now capture.

**Corollary that inverts the usual instinct: a mobile app pinning its TLS certificate blocks you from OBSERVING it, not from BEING a client.** Kia Access pins — mitmproxy logs `client disconnected during the handshake` for its API host while other hosts decrypt fine through the same proxy seconds later — so a phone-proxy capture is impossible on a stock device, and entirely unnecessary, because that same API answers plain server-side `curl` with the OSS constants. Three rounds of proxy setup went by before that probe was run. **When the target has a mobile app AND an open-source client exists, probe before you proxy.** Never jailbreak or re-sign an IPA to read an API you can simply call. (Telling pinning from an untrusted CA is easy to get backwards: pinning = that ONE host fails while others decrypt; untrusted CA = everything fails. Confirm at least one host decrypting in the same window before calling it pinning — a log filter that hides the successes will make you conclude the opposite.)

Check the web surface early too: **a site's dashboard may be read-only while the mobile API carries the writes.** Kia's portal shows status but exposes no lock/unlock/climate/charge control anywhere, and its server-side proxy's routing headers list only read endpoints. Enumerate it before assuming it can replace the app's.

**A typed-RPC SPA ships its whole API contract — read it instead of capturing.** ServiceStack (and any DTO-per-endpoint stack) compiles each request type into the JS bundle as a class carrying its own `getTypeName()` / `getMethod()`, so the wire name, HTTP verb and full field list of EVERY endpoint are extractable mechanically — no DevTools, no HAR:

```js
[...src.matchAll(/getTypeName\(\)\{return"(\w+)"\}(?:getMethod\(\)\{return"([A-Z]+)"\})?/g)]
// then walk back to the preceding `constructor(` and collect T(this,"Field")
```

Try the metadata endpoints first (`/metadata`, `/types/typescript`, `/openapi`, `/swagger-ui`) — production usually 404s them all, which is what makes the bundle the only machine-readable source. pickuppatrol yielded 41 DTOs with verbs and fields this way in one pass.

**But the DTO classes give you the request SHAPE, not the payload VALUES — and the call sites live in lazily-loaded route chunks.** A field list does not tell you that `Plans` is an array of one entry per date, or that "revert to default" is the same call with a null id. Find the chunk that builds the payload: open the SPA route in a signed-in tab and diff `performance.getEntriesByType('resource')` before/after navigating; the new `*.js` is the one to read. Two of pickuppatrol's writes were only decidable this way — and one of them turned out to have no endpoint of its own at all (weekly defaults are a read-modify-write PUT of the whole parent record), which no amount of staring at the DTO list would have revealed.

**And the URL the code composes may not be the URL on the wire — an interceptor
can rewrite it, and an endpoint probe will not tell you.** honeybook-mcp's
`get_flow` was built by reading the shipped flow app, correctly: `_fetchFlow`
really does compose `/api/v2/flow/<id>/active`. The wire call is
`/api/v2/**client**/flow/<id>/active?ctxc=<companyId>`, because a shared axios
interceptor one layer below does `url.replace("/api/v2/", "/api/v2/client/")`
and injects `params.ctxc` from a store. **Neither `/api/v2/client/flow` nor the
`ctxc` assignment is greppable as a request path** — the literal does not exist
in the bundle, so a search for endpoints finds only the pre-interceptor form.

Worse, the obvious check CONFIRMS the wrong answer: both paths return a
byte-identical `404 {"error_type":"HBUnauthorizedError"}` unauthenticated, so
"the route exists" was true of a URL that never works. It shipped, and the
first real call was a 400 whose body says only "Unexpected server error".

So: read the bundle to learn the SHAPE and to find candidates, and take **one
HAR of the real call** before writing the client — an authenticated capture is
the only artifact that shows the request as sent, headers included. It also
hands you things reading cannot: `hb-api-client-version` turned out to be
load-bearing (without it every call is that same 400), while
`hb-api-fingerprint`, which looks equally required, is ignored — isolated in
three requests by removing one header at a time. Budget the capture; it is
cheaper than shipping a tool whose only real-world test fails.

**Auth preference order — avoid requiring the browser bridge at runtime.** fetchproxy needs the Transporter extension + a signed-in tab, so it's the heaviest thing to ask of a user. Pick the FIRST that authenticates cleanly, and even then keep the bridge off the hot path:

1. **username/password in `.env`** — a real server-side login (the cookie-session archetype below; or a bearer/token if the API offers one). No browser, no extension. Always try this first — but **grep the login page for a captcha before you build on it**: `grep -oiE 'recaptcha|hcaptcha|turnstile|arkose' login.html`. A site can present a perfectly ordinary form POST (`csrf_token`/`login_email`/`login_password`) and still inject a captcha token at submit time, in which case the endpoint answers `400 {"error":"Human verification code missing"}` and **no server-side login is possible** — drop to option 2. Thumbtack looks exactly like the artsonia archetype until you look for `recaptchaSiteKey`. One `grep` decides the archetype; probe with a deliberately nonexistent `@example.com` address, once, never a real account.
2. **fetchproxy *bootstrap*** — use the bridge ONCE to capture auth from the signed-in tab (its session cookie / storage, via `createBootstrapOpts({ bootstrap: { cookieKeys: [...] } })` → the `read_cookies`/`read_local_storage` capabilities), then make every actual request with plain node `fetch` carrying that cookie. The bridge touches only the handshake, not the workload. **Bot-walled + no server-side login variant** (DataDome/PerimeterX-fronted, NO username/password form and NO token exchange — the only credential is what the browser's own API requests carry): capture the **request headers verbatim** via `createBootstrapOpts({ bootstrap: { captureHeaders: [{ host, path: '/api/*', headerName: 'cookie' }, …any app-key header like `x-at-key`] } })` (the `capture_request_header` capability → `session.capturedHeaders`). Snapshotting the live `Cookie` header (incl. the short-lived anti-bot cookie) beats enumerating named `cookieKeys` you can't fully see, and grabs request-only headers (app keys) that aren't in any store. Drive it with **`CookieSessionManager`** whose `isExpired` treats **403 as well as 401** as expiry — a 403 = the anti-bot cookie went stale → re-capture — and cache the no-config error via `isPermanentError` so a missing session doesn't re-run the bridge on every call. A non-JSON 2xx read is almost always a bot-challenge interstitial: throw an actionable "refresh a signed-in tab" error, don't `JSON.parse` it blind. (ofw-mcp / alltrails-mcp.)
3. **full-on fetchproxy** — every request routed through the signed-in tab. Only when the site can't be reached server-side at all (a hard bot-wall on every endpoint).
4. **other** — if none of the above authenticate cleanly, propose changes (to `@fetchproxy/server` / the bridge, or a different capture) to get a working *minimal-bridge* auth; don't silently settle for full-on fetchproxy.

**Whichever you land on, use node `fetch`/GET for everything the bridge isn't strictly needed for** — route only the unavoidable calls (auth, or specific walled endpoints) through fetchproxy and node-fetch the rest. Don't reach for fetchproxy just because a sibling did; reach for it only when server-side auth/fetch genuinely fails.

- **bearer / direct API** (splitwise, tempo, ioffice, app-store-connect, skylight, gemini-mcp): `client.ts` does `fetch` with a bearer/token header. Use `createApiClient` if it fits; always route error bodies through `formatApiError`/`truncateErrorMessage`. No fetchproxy. **Non-`Authorization: Bearer` auth → write a thin custom `fetch` client instead of `createApiClient`** — its `getToken` only emits `Authorization: Bearer …`. APIs with a custom auth header (`x-goog-api-key`), a model/id baked into the path (`/models/{m}:generateContent`), or binary-in-JSON responses are cleaner as a small `call()` that still uses `McpToolError` + `truncateErrorMessage` (gemini-mcp). **Binary-OUTPUT tools** (image/file generation): write bytes to a configurable dir (`<SVC>_OUTPUT_DIR` → cwd) and return the path, with an `inline` flag for base64 via `imageResult`, and non-overwriting filenames — don't dump megabytes of base64 into the result by default. These create local files / cost money but don't mutate remote state, so they are **not** `confirm`-gated (confirm is for remote writes). **Tiered APIs can answer `401` (NOT `402`/`403`) for endpoints ABOVE the key's plan** — FlightAware AeroAPI returns `401` titled "Invalid API key" with a *tier* detail for alerts/history/canonical on the free tier, so a VALID key looks "invalid." `createApiClient`'s `onUnauthorized`/`onRateLimited` take **NO args** (they can't see the response body), so don't let `onUnauthorized` flatly assert "key invalid" — word it to name BOTH causes (bad key OR insufficient tier) and mark the tier-gated tools' descriptions. **Billed / rate-limited reads → a small per-path response cache** (in-memory, TTL via `<SVC>_CACHE_TTL`, bounded + oldest-evicted, writes never cached) cuts duplicate spend; give *reference* data (airport/operator metadata, canonical lookups, routes) a much longer **second tier** (`<SVC>_STATIC_CACHE_TTL`, e.g. 1h vs 15s) selected per-tool via `get(path, { cache: 'static' })` (flightaware-mcp).
- **cookie-session / username+password** (artsonia; many school/portal sites): a classic server-rendered `.asp`/`.php` site — no public API, no JSON store, no bot-wall — that accepts a real **username/password form POST** and hands back an **HttpOnly session cookie**. No browser bridge needed. `src/auth.ts` posts the login form and captures all `Set-Cookie`s into a cookie jar (use `parseCookieJar`); `src/client.ts` fetches with the jar over plain node `fetch` (`redirect: 'manual'` on the login POST so the 302's `Set-Cookie` is readable). Detect session expiry by a redirect back to the login page → **single-flight re-login** (one shared in-flight promise, à la `TokenManager`). Deferred-config reads `<SVC>_USERNAME`/`<SVC>_PASSWORD`. Parse the server-rendered HTML with `node-html-parser`. Keep `@fetchproxy/server` only as an OPTIONAL, env-selected fallback — not the default. See the **cookie-session / classic-form specifics** below.
- **fetchproxy / browser-bridge** (realty cohort, reservations, finance, school): the site has no public API AND can't be authed/fetched server-side (try options 1–2 above first), so requests go through a signed-in browser tab via `@fetchproxy/server`. `src/transport-fetchproxy.ts` wraps it; session tools expose/select accounts. Use `@chrischall/mcp-utils/fetchproxy` **only on `@fetchproxy/server` >= 0.11** (it re-exports 0.11+ APIs). Repos on older pins keep their own transport until a deliberate bump. Even here, node-fetch any endpoint that doesn't actually need the bridge.
- **username/password + MFA → one-time bootstrap, then a refresh token** (kiaaccess): a real server-side login that answers `nextAction: MFA_REQUIRED` with an OTP key, needing `sendOTP` (channel `SMS`/`EMAIL`) then `verifyOTP` before it yields a session. **The question that decides the whole architecture: does the refresh token skip MFA?** Test it explicitly and early — re-auth using only the stored token and see whether a challenge comes back. If it does skip (Kia's `rmtoken` does, and is not rotated), MFA is a ONE-TIME bootstrap: persist the token via `SessionStore` (0600) and mint sessions with `TokenManager`, and hosting on mcp-host stays possible. If it does not, every session needs a human and both the MCP and any hosting are far less useful — you want to know that before building either. Expose the bootstrap as explicit tools (`<p>_start_login` / `<p>_send_otp` / `<p>_verify_otp`), and note the OTP window is often ~2 minutes. **NEVER auto-retry a rejected credential**: these APIs count attempts (`loginAttempt`) and escalate to reCAPTCHA (`enforceRecaptcha`), which breaks server-side auth for that account *permanently* — a retry loop is not a nuisance here, it is destruction of the only auth path you have.
- **rate-limited public API — no-auth reads + OAuth-grant writes** (musicbrainz): a real public REST API (no key needed for reads, just a descriptive **`User-Agent`**) with a **hard rate limit** and OAuth2 only for writes. `client.ts` is a thin custom client (not `createApiClient` — see the throttle/503 gotcha) with one `get()` (no auth) and one `write()` (bearer + `client=` param). **Partial deferred-config:** reads boot with NO creds, so there's no read-side `configError`; only the OAuth `write()` path defers its config error (missing `<SVC>_OAUTH_CLIENT_ID/SECRET/REFRESH_TOKEN`) to the first write. Confirm-gated writes route through `write()`. See the **rate-limited / OAuth-writes specifics** below.

### fetchproxy specifics (hard-won — each was a real failure in the musescore-mcp or honeybook-mcp builds)

- **One shared port: `37149`.** The whole fetchproxy fleet binds the SAME concentrator port — the **Transporter** browser extension dials that ONE port, and servers host/peer-elect on it (first to bind is host; the rest are peers tunneling through it). A new fetchproxy MCP MUST default to `37149` (`DEFAULT_PORT = 37_149`; env override `<SVC>_WS_PORT`). Give it a "unique" port and the extension never connects (`ws://127.0.0.1:NNNNN … ERR_CONNECTION_REFUSED`) — it has no idea your port exists. Copy the port from a sibling (zillow/redfin); don't pick a new one.
- **Lazy bind + first-use pairing.** `listen()` reserves nothing; the port binds + role-elects on the FIRST verb call (or `connect()`). A brand-new server's identity (`~/.fetchproxy/identity/<server>.json`, auto-created) is unknown to the extension, so the first request returns `pairing required … pair code: NNN-NNN` — the user approves it ONCE in the Transporter popup (TOFU, per-identity, persists). Onboarding a new fetchproxy MCP = (1) default port 37149, (2) trigger one call (`<svc>_healthcheck`), (3) approve the pair code in Transporter.
- **The grant is per-identity AND per-scope — pairing is NOT approve-once-forever.** The extension gates every request against the scope approved *at pair time*, so ANY widening or change of `declare` — a new cookie key, a different `storageKey`, an added pointer — is refused for every already-paired user with `<kind> keys not in declared set: X`. The remedy is not a retry and not an update: the user must **revoke the MCP in the Transporter popup, re-run, and approve the new scope**. Two consequences. (1) A declaration change is a BREAKING upgrade for existing users — say so in the release notes; a silent patch bump strands everyone who already paired. (2) Test it the way users hit it: revoke, then re-pair. honeybook-mcp 0.4.5 moved one storage key and refused every existing session until re-approval.
- **Defer to the typed `.hint`; only append your own copy to UNCLASSIFIED errors.** The Pattern A `auth.ts` catches bootstrap failures and re-wraps them with service-specific advice ("open the magic link in Chrome, then retry"). `@fetchproxy/server` types `FetchproxyScopeError` and `FetchproxyNoTabError` (both `FetchproxyHintedError`) precisely BECAUSE that re-wrap buries the remedy — its own class doc says users saw the bare "keys not in declared set" bolted onto unrelated auth copy with no mention of re-pairing. Most templates special-case `bridge_down` and nothing else, so the hinted errors fall through to the generic branch and users get the correct remedy and contradicting advice in one string. Match the FAMILY by duck-type — `err.name.startsWith('Fetchproxy')` AND a non-empty string `err.hint` — and surface `.message` unmodified. Do NOT branch on `FetchproxyHintedError`: `FetchproxySessionNotReadyError` (pairing not yet approved, and its hint carries the pair code) is NOT one of its subclasses, so the base class silently misses the single most common first-run failure. `instanceof` is unreliable anyway when a duplicated `@fetchproxy/server` copy is installed. The name prefix rather than "any error with a hint" is also deliberate: an unrelated rejection that happens to carry one (an HTTP 502 with `hint: 'retry later'`) is not auth guidance and must not displace the env-var advice. See `fetchproxyHintOf` in `src/auth/index.ts` for the reference implementation.
- **Require ONLY the fields the upstream actually needs — probe to find out which.** A capture that throws on every declared field turns a cosmetic upstream rename into a total outage. honeybook-mcp demanded a trusted-device id and a per-device `hb-api-fingerprint`; the API returns 200 without either, so two non-essential fields could each have taken the MCP down on their own. Before making a field mandatory, send the real header set MINUS that field and record the status. Send optional values only when present — never let an absent one serialize as the string `"undefined"`/`"null"` into a header.
- **Auth expiry is not always 401 — find the real signal empirically.** HoneyBook answers a revoked token with **404 + `HBUnauthorizedError`**, so a 401-only check reports an opaque "error 404" instead of "re-capture your session". Send a deliberately bogus token once, record status AND body, and gate on the body when the status is ambiguous (`status === 404 && body.includes('HBUnauthorizedError')`) so a genuinely missing resource stays a plain 404.
- **Storage keys drift — pin the current one, keep a legacy fallback, and name the full path in the error.** Apps migrate client state between keys (HoneyBook moved portal auth out of the AngularJS `jStorage` blob into a React-era key, leaving one field behind). Read the current key, keep a pointer at the old one where it still carries something, and put the full `KEY./pointer` in the failure message: `HB_AUTH_TOKEN not found at jStorage./HB_AUTH_TOKEN` is what turned that outage into a five-minute diagnosis.
- **Probe auth requirements from INSIDE the page — return status codes, not values.** `claude-in-chrome` redacts anything token-shaped (`[BLOCKED: …]`), which is a feature here: rebuild the client's exact header set in the signed-in tab, fetch a real endpoint, and report ONLY `{status, byteLength}`. You get a definitive per-header matrix (drop each in turn) without a credential ever entering the transcript, and it runs as a same-origin in-tab fetch so no bot wall sees Node.
- **Parse the SSR JSON store; verify against RAW-FETCHED bytes, not the hydrated DOM.** Modern SPAs render NO cards/tables in the fetched HTML (client-hydrated) — the data is an entity-encoded JSON store (a `__NEXT_DATA__` analogue, often attribute-escaped: `&quot;`/`&amp;`). The MCP parses what fetchproxy fetches = raw SSR, which ≠ `document.querySelectorAll` in a live tab. Verify your parser against the actual bytes: in a signed-in tab run `await fetch(path,{credentials:'include'}).then(r=>r.text())` and parse THAT. Recover-from-entities + bracket-match (don't regex nested JSON); skip any bot-manager fields (`bm_*`, `client_ip`, `ja3`/`ja4`) that ride along in the store.
- **Tighten Cloudflare detection.** The shared `classifyBotWall` covers perimeterx/datadome; for Cloudflare-walled sites detect the interstitial by DEFINITIVE markers only — `_cf_chl_opt` and `<title>Just a moment`. Do NOT match `cdn-cgi/challenge-platform` / `challenges.cloudflare.com` (Cloudflare inlines those on CLEARED pages too) or gate on body size — that false-positives on legit pages under ~80 KB (it made every score-page fetch wrongly report a bot-wall while the bigger search pages sailed through, so "search works but detail pages fail" is the tell).
- **The bridge does `fetch()` — it can't navigate, follow cross-origin redirects, or stream binaries.** Endpoints that only work as a browser NAVIGATION — file downloads with `Content-Disposition: attachment`, or a same-origin endpoint that 302s cross-origin to a presigned S3 URL — can't be fetched: the bridge's `fetch` throws on the cross-origin redirect, and a server-side node `fetch` hits the Cloudflare wall (403). Such a tool can only **resolve** the URL (return it for the user to open), not download the file. Don't scrape the page's render tiles to fake it.
- **Capture response SHAPES through the bridge itself, not by replaying the captured cookie from Node.** On a cookie-bootstrap MCP (alltrails), DataDome can `403` EVERY Node replay of a freshly captured cookie on a day when an in-tab fetch sails through — a shape-capture probe built on the real client just loops capture→replay→403. Probe via `createFetchproxyTransport({serverName, domains, defaultSubdomain})` → `requestJson(method, path, {headers})` instead: the request runs as a same-origin in-browser fetch inside the signed-in tab, so the bot wall never sees Node. Two details: send the site's app-key headers (`x-at-key` etc.) explicitly — an in-tab `fetch` does NOT add them; and when a bootstrap capture window sits at "waiting for next request", `open "https://<site>/…"` from Bash feeds it (the page load fires the API calls). The alltrails captures done this way immediately exposed a live bug (`/me` returns `{users:[…]}`, not the `{user:…}` the code read) — which is the point of capturing over guessing.
- **Verify a real SUCCESS, at the right layer, before coding the gate.** Downloads/navigations DON'T appear in XHR/`fetch`/HAR monitoring — watching those and concluding "nothing happens" is wrong. Confirm an actual artifact end-to-end (a file lands on disk) and read the JSON store for the real gate field before encoding it. (Cost of skipping this: a download gate built on the wrong field — `hasAccess`, an entitlement flag — instead of `is_free`, which refused every actually-downloadable score.)

### cookie-session / classic-form specifics (hard-won — the artsonia-mcp build)

- **Capture a JS-driven login by instrumenting it, not from static HTML.** Modern login forms inject the `Username`/`Password` `<input>`s via JS, so the raw HTML has only hidden fields. You can't type a password yourself (safety rule) — capture the real request by hooking `submit`/`fetch`/XHR while the USER logs in once, then replicate the form POST. (Artsonia: `POST /members/login.asp`, body `Username&Password&TargetUrl&Action=login`, `redirect:'manual'` to read the 302's HttpOnly cookie; no CSRF on these old stacks.)
- **A 302 / redirect-away is NOT proof a write persisted.** Old form handlers 302 to a content page on BOTH a real save and a silently-ignored one. Verify every write by RE-READING the resource — never trust the status code. (Cost of skipping: `set_notifications` reported success on a 302 that saved nothing.)
- **Submit a checkbox's real `value`, not `"on"`.** Classic checkboxes carry `value="Y"`; sending `name=on` is silently dropped. Capture each control's real value — checked → `name=<value>`, unchecked → omit it (as the browser does).
- **One field in a master form = read-modify-write.** If a toggle lives in a big profile form, re-POST the WHOLE form: re-send every current field verbatim (hidden ones at their real values, e.g. `DidChangePassword=N` not `0`), BLANK the password fields, flip only your target. Never send a password.
- **Verify INNER selectors against the live DOM, not just the container.** The data's in the server-rendered HTML (parse with `node-html-parser`) — top-level selectors (`.artist-card`) confirm trivially, but the child selectors you guess for a fixture (`.name`, `.date`) are usually wrong. Run the real parser logic against `await fetch(path,{credentials:'include'}).then(r=>r.text())` and diff the output before trusting it.
- **Recon through claude-in-chrome redacts secrets.** It blocks content that looks like cookies/query-strings/tokens (`[BLOCKED: …]`), so extract STRUCTURE — tag/class trees, form field NAMES, URL path + param KEYS — never raw HTML/values, and never log a captured password/cookie. Media is often a public CDN (fetchable server-side, no auth) whose `Last-Modified` header is a free per-item date when the HTML exposes none.

### rate-limited public-API / OAuth-writes specifics (hard-won — the musicbrainz-mcp build)

- **A hard rate limit needs a PROACTIVE throttle, not just retry — and `createApiClient` only retries 429.** APIs that cap you (e.g. MusicBrainz: 1 req/s) signal an overage with **503 + `Retry-After`**, NOT 429, so `createApiClient`'s built-in 429 retry never fires and it surfaces a raw error. Write a thin custom client whose every call (reads AND writes) funnels through one **serialized min-interval queue** (`src/throttle.ts`: a promise chain that spaces request *starts* ≥ limit apart, with injectable `now`/`sleep` for tests) so concurrent tool calls line up instead of bursting; also retry 503/429 honoring `Retry-After`. One throttle, one client — never hit the API outside it or you bypass the spacer. A descriptive `User-Agent` is mandatory (these APIs block generic/empty UAs).
- **OAuth-grant writes: `createOAuth2Refresher` + a tiny in-memory token cache.** For the write path, `createOAuth2Refresher({ endpoint, refreshToken, params:{client_id,client_secret} })` does the `refresh_token` grant; cache the `{accessToken, expiresAt}` and refresh ~60s before expiry (the refresher already shares a single in-flight exchange, so concurrent writes don't double-refresh). The **human must register the app and supply `client_id`/`secret`/`refresh_token`** (an agent never sets creds), and **live write-verification is GATED on that** — unit-test the write shapes meanwhile.
- **Capturing the refresh token: verify redirect rules against the LIVE registration form, then use a `http://localhost` loopback listener.** The provider's OAuth *doc* is often stale (MusicBrainz's said `oob`/`localhost`; the live form rejected both, demanding a **reverse-DNS** scheme for "installed apps") — read the actual form, not the doc. You can't type the user's password or click Allow for them, and a custom-scheme (`app://…`) redirect can't be captured (Safari won't expose the redirected URL). So: generate the authorize URL **with PKCE** (`code_challenge=S256`), run a one-shot `http://localhost:<port>/` listener that captures `?code=`, exchanges it (`grant_type=authorization_code` + `code_verifier`), and writes the refresh token into `.env`. The human just clicks Allow.
- **Write responses may be NON-JSON** — MusicBrainz answers a successful write with XML / `{"message":"OK"}`, so `write()` returns the **raw body**; don't blindly `JSON.parse` it (keep the same `formatApiError`/`McpToolError` handling for non-2xx).
- **The re-read used to verify a write can itself be CACHED.** Re-reading after a write (the skill's "a 200 is not proof, re-read" rule) can serve a **stale cached body** — a `/ws/2` GET showed the old state right after a successful write/withdraw, so the write looked like it failed when it hadn't. **Bust the cache with a unique nonce query param** (`&_=<nonce>`) on the verification read. (Read tools are unaffected — this only bites write-verification re-reads.)

### Verifying a write actually landed (hard-won — the kiaaccess-mcp build)

"A 302 is not proof a write persisted" generalises, and the *verification code itself* is where the bugs live. Every one of these produced a confident false green against a real vehicle:

- **A field that advances on every read poisons the whole diff.** Kia's `syncDate` ticks on each poll, so including it in a before/after comparison made **every** command report success — a write tool that can never report failure. Snapshot ONLY the fields whose change proves the thing; exclude timestamps explicitly and name the exclusion in code (`CHANGE_DETECTION_EXCLUDED_KEYS`).
- **Reading a field that doesn't exist compares equal to itself.** `undefined === undefined`, so a typo'd or guessed proof field silently reads as "nothing changed". Dump the real response's key set once and pin the exact path; don't infer it from the request body's vocabulary (Kia's request says `airCtrl`, the status object nests it under `climate.airCtrl`, and a flat `airCtrlOn` — the obvious guess — does not exist).
- **A proof field that is real, readable, and simply never moves for THIS operation.** The third sibling of the two above, and the sneakiest: the field exists, you read it correctly, and the write genuinely succeeded — but the edit didn't touch that field. Every PickUp Patrol dismissal option requires a note, so changing only the note is an ordinary edit, and a verifier comparing just `TransportationId` passed without observing anything. **Derive the proof set from what the write actually REQUESTED, not from a fixed field list** — if the call sent a note, the note is part of the proof. Normalize whitespace so a service-side trim isn't read as failure.
- **A read may return the STORED override, not the EFFECTIVE value.** Before verifying by re-read, establish which one the endpoint gives you. `GetPlanEdit` returns `null` for a date with no specific plan *even when a weekly default applies*, so expecting the merged default reported every successful "clear/reset" as a failure. Any system with defaults + overrides (settings, schedules, pricing tiers) has this fork: a successful reset reads back EMPTY, not "the default".
- **Those two bugs CANCEL.** A non-existent field (always "unchanged") plus a ticking timestamp (always "changed") produced a green verdict for a command whose effect was never observed at all. Assert against a *known* state transition end-to-end at least once before trusting the harness.
- **A status endpoint that ACCEPTS an action id may not report that action.** Kia's `cmm/gts` takes an `xid` and returns unrelated global flags; polled through a real command it never changed. Gating on it waits forever. Verify the poll endpoint actually moves before building a wait loop on it.
- **Sub-resources can be absent unless requested.** Kia's whole `climate` block only appears when the status call sets `airTempRange:"1"` + `seatHeatCoolOption:"1"`; with the defaults it is missing, so the proof field reads `undefined` (see above). Request the flags your verifier depends on.
- **The domain may not have the field you expect.** On an EV, `engine` stays `false` with climate running — the ignition proxy is `ign3`. Gating an EV's climate check on `engine` always reports failure.
- **Snapshot the pre-write state to a durable file BEFORE the first write, and never pipe a write-then-restore script through anything that can close stdout.** `node live-write.mjs | head -80` kills the process on SIGPIPE — and if it dies between the write and the restore, real state stays changed. Worse, re-running then reads the MUTATED state as "original" and faithfully restores the wrong value, which is how a PickUp Patrol student's Friday pickup note stayed narrowed until an earlier read-probe capture was used to put it back. Write the full output to a file and read the file; keep the pre-write capture outside the script's own memory.
- **Choose live-test edits that fail SAFE.** Pick a change whose failed restore is a no-op or the conservative side: set a date to the option its own weekday default already uses (identical effective outcome), and *narrow* a permission rather than widening it. Cross-check the restored value against a sibling record that was never touched — three students with the same pattern made the correct value unambiguous.
- **Order live write tests so the system ends where it started, and re-read at the end.** Sequence `unlock → lock`, `start → stop`, `stop-charge → start-charge`; restore any setting you change. Then re-read once more — a charge-limit test left the car not charging even though each step "passed", and only the final check caught it.

## Hosting on mcp-host — optional, on request

**`mcp-host` (`~/git/mcp-host`, deployed at `mcp.nullnet.app`) hosts any stdio MCP in the fleet.** Point it at an **npm package** or **GitHub repo** and it serves that server to claude.ai as a remote connector — streamable HTTP, OAuth 2.1 + PKCE, per-MCP grants. A Cloudflare Worker gateway fronts a Fly.io runner that installs the source and supervises the stdio child.

**Hosting is a REGISTRATION, not a code change.** This is the whole point, and it replaces the old per-repo Cloudflare Worker connector: there is no `src/worker.ts`, no `wrangler.jsonc`, no `OAUTH_KV` namespace, no second vitest config, no `@chrischall/mcp-connector` harness, and no deploy workflow. The stdio server you already built *is* the hosted server.

```sh
export MCP_HOST_URL=https://mcp.nullnet.app
export MCP_HOST_ADMIN_TOKEN=...
alias mcp-host='node ~/git/mcp-host/packages/cli/src/index.mjs'

mcp-host secret set SPLITWISE_API_KEY --value 'xxx'      # encrypted in D1, resolved at spawn
mcp-host register --slug splitwise --npm splitwise-mcp \
  --secret-env SPLITWISE_API_KEY=SPLITWISE_API_KEY
# -> prints connectUrl: https://mcp.nullnet.app/c/chris/splitwise/mcp
```

Then in claude.ai: Settings → Connectors → Add custom connector → paste the `connectUrl`, sign in on the authorize page, press Connect. Each hosted MCP is its own connector with its own grant; revoking one never touches another.

### Ship a `mint.yaml` — the registration writes itself

**Every full MCP gets one, at the repo root.** It is how the server tells mcp-host what it needs; without it, whoever registers is guessing from the README, and every guess wrong is a connector that registers cleanly and fails later. mcp-host reads it at the exact pin and fills the register wizard in from it (`docs/MINT-MANIFEST.md` in that repo).

```yaml
version: 1
name: Splitwise
slug: splitwise
env:
  - name: SPLITWISE_API_KEY
    secret: true              # propose a secret REFERENCE, never a literal
    required: true
    help: From splitwise.com/apps
```

That is a complete file. Add only what is true of this MCP:

- `command: { bin: <name> }` — **required when package.json declares more than one bin**, or the install refuses (canvas-parent-mcp shipped broken on exactly this).
- `dependencies:` — a binary the server shells out to, as a GitHub release asset (`repo`, `tag`, `asset` glob, `bin: [name]`), or extra npm packages. This is the gogcli case.
- `state: { dataDir: true, reason: <why> }` — **the reason is required**: it is what an owner judges. Say what is kept and what breaks without it ("keeps its device id under `$HOME`; without it every cold start re-enrols").
- `identity: { perUserChild: true }` + `auth: { fields | flow }` — only for an MCP that authenticates as its CALLER. `auth` requires `perUserChild`.
- `egress: { allow: [host, …] }` — enforced only on the isolated tier, a proposal everywhere. **Deriving this correctly is the hard part — see below.**
- `tools: { enable: [...] }`, `build:`, `subdir:`.

**There is NO `bridge` / `bridgePortEnv` / `runtime` field.** Those are *registration* fields, set over the control API (§*Browser-bridge MCPs CAN be hosted*) — the manifest schema has no column for them, so a bridge repo cannot declare itself bridged. State the requirement in a **comment** and declare `state.dataDir: true` (which the API requires for `bridge`) with its reason. Do NOT put it in `summary`: that is user-facing wizard text, and folding an internal hosting note into it fails review.

**Egress: a URL-literal grep is both noisy AND incomplete.** Across a fleet-wide rollout this was the single biggest source of failed reviews, in *both* directions — an over-grant widens the sandbox for nothing, an under-grant makes every tool report "could not reach the API" on the isolated tier. Rules, each paid for by a real failure:

- **Strip comments first.** A host in a doc link or a prose note is not egress (booli's `challenges.cloudflare.com`, app-store-connect's `developer.apple.com`).
- **Also scan bare-domain literals** — a hostname allowlist lives in a constant (`ALLOWED_APEX = 'accessoticketing.com'`), and a URL-only scrape missed that repo's *only* host.
- **The two mistakes do NOT cost the same — bias toward granting.** An over-grant is a review nit; an under-grant means every tool reports "could not reach the API" on the isolated tier, which reads as an outage rather than a config error. When a host is genuinely ambiguous, include it and say why in a comment.
- **A `domains: [...]` fetchproxy declaration says what the BROWSER reaches — not necessarily what the SERVER fetches.** For a full-bridge repo it is usually both (redfin's `domains:['redfin.com']`), so it still beats guessing at a bare-domain literal. But a *bootstrap* repo uses the bridge only to lift a credential and then makes every real call as a plain Node fetch somewhere else: honeybook declares `honeybook.com` + `hbportal.co` to the bridge while `client.ts` fetches only `api.honeybook.com` — listing the declared pair failed review. Check which calls actually leave the Node process before treating a declaration as server egress.
- **Not egress:** a URL inside a prose/error string (`partner.getyourguide.com`) — *unless* the host also appears as a bare `https://host/…` base literal, or you will drop a real base (musicbrainz's `WS_BASE`); an `xmlns="http://host/…"` XML **namespace** (`topografix.com`, and skylight's `s3.amazonaws.com`); an `origin:`/`referer:` request **header** value (housecallpro's `client.housecallpro.com`); a bot-wall vendor named only inside a detection check (`body.includes('awswaf.com')`).
- **"It only appears in a `return`" is NOT sufficient to exclude a host — this single assumption caused every under-grant.** A URL *builder* returns a URL the code then fetches, and by shape it is indistinguishable from a link handed to the user. artsonia (`artworkImageUrl()` → `images.artsonia.com`, fetched in `download.ts`) and housecallpro (`pro.housecallpro.com`, fetched with `redirect:'manual'` to resolve a short link) both failed review this way. Follow the builder to its call sites; a genuine link-only host is one that nothing fetches (`pay.google.com`, `ssl.cdn-redfin.com`, `matterport.com`).
- **Validation lists cut both ways.** A bare host in an accepted-hostname array is usually *not* egress when the fetch then targets a pinned base (maxpreps parses a user URL, then fetches `www.maxpreps.com`) — but IS egress when the server fetches the user-supplied URL itself (accessoticketing). Mechanical classification cannot settle this: surface bare-only hosts for a human read rather than auto-granting them.
- **Runtime hosts appear nowhere as literals** — a signed `upload_url` returned by the API, a Firebase `databaseURL` from a config blob, `${bucket}.s3.${region}.amazonaws.com`. Grep for `databaseURL`/`upload_url`/`presigned` and say so in a comment (or allow the apex) rather than silently under-granting.
- **A tenant/district service gets NO `egress` block at all.** When the host is per-deployment (`WORKDAY_HOST`/`WORKDAY_TENANT`, a district's Infinite Campus host, an iOffice tenant) any fixed allowlist is wrong by construction — write a comment naming the variable to derive it from.
- **Do not list a bare apex "for safety" next to the subdomain you actually fetch.** Seven repos were nitted for exactly this in one rollout (`creditkarma.com` beside `api.` + `www.`, `signupgenius.com`, `resy.com`, `ourfamilywizard.com`, `onehome.com`, `appstoreconnect.apple.com`, `www.etix.com` beside its parent). The apex was in each case a fetchproxy `domains:` declaration, an `Origin:`/`Referer:` header, or a returned link — never a server fetch. This does not contradict "bias toward granting": that is for a host you cannot resolve, not one you have *checked* and found unfetched. Grep for a bare `https://<host>` base literal; if the only hits are headers, links and the bridge declaration, leave it out.

**Two more nits worth pre-empting, both trivial and both cost a review round:**

- **Check `.mcpbignore` before adding `mint.yaml` to it** — most fleet repos already carry `*.yaml` / `*.yml` globs, which cover it. Seven repos were nitted for the redundant line. (The `files` entry in `package.json` is still required; only the ignore line is often already handled.)
- **`state.reason` is read as a factual claim about what is on disk, and gets checked.** untappd's said `$HOME` persists "the saved session/token" when the token is in-memory only and what actually persists is a check-in cache DB — the reason is the thing an owner judges `dataDir` on, so an inaccurate one is worse than a terse one. Name the actual file and what breaks without it.

**Two more, both cheap and both cost a review round:** copy `env` help **verbatim from the repo's own `server.json` / `manifest.json` descriptions** (most repos already have them) or derive it by reading the code — never invent it, and never invent a URL (a `/apps` that should have been `/apps/register` failed a PR). And do **not** filter out timeouts/TTLs/dirs/debug flags as "internal": they are user-settable knobs, and omitting one fails review too — `GYG_REQUEST_TIMEOUT_MS`, `OFW_DEBUG_LOG` and tripadvisor's three cache/debug vars were each nitted for being absent. **The roster is whatever the repo documents, not whatever `readEnvVar('X')` greps up:** tripadvisor's three are documented in `README.md` with defaults and wired through `.mcp.json`, yet a naive grep for the literal call missed all three. Read `README.md` and `.mcp.json` as well as the source, and take the help text from the README table when it has one.

**One repo is not always one server — check the shape before generating anything.** `<name>-mcp` does not mean "an MCP server lives at this root":
- A **workspace monorepo** whose root is `private` publishes nothing from the root, so a root manifest is never read. Each **published package** needs its own, because an `--npm` registration reads *that package's* tarball (gogcli-mcp: root private, nine published packages, so nine manifests — each with its own `command.bin`).
- A repo can be a **library wearing an `-mcp` name**: `realty-mcp` holds only `@chrischall/realty-core`, with no bin, no `main`, no `src/`, no `runMcp`. It is not hostable and correctly has no manifest. Tell it apart by looking for a bin + a `runMcp` entrypoint before writing a file that would say nothing.

Two rules to keep in mind while writing one:

1. **It proposes; it never applies.** The file is not covered by the tarball's integrity check, so nothing in it reaches a child until an owner reviews and saves. Do not treat it as configuration you control — treat it as the accurate answer to "what does this need?".
2. **Never put a secret VALUE in it**, including as a `default`. A `default` on a field marked `secret`, or on a secret-shaped NAME, is refused — a credential in a file in a public repo is a leak, not a default.
3. **It MUST be in `package.json` `files`, or an npm registration reads a blank wizard.** For an `--npm`-sourced registration the "exact pin" mcp-host reads is the published TARBALL, not the GitHub tree — so a `mint.yaml` omitted from `files` is simply absent, and the register wizard comes up empty (no egress, no env, no state) with no error. Same silent-omission class as `"skills"` under §*Authoring the fpx skill*, and it hid a whole build: alphaportal-mcp declared `egress: [api.alpharoute.app]` but `files` listed only `dist`/`.claude-plugin`/`skills`/`.mcp.json`/`server.json`, so the isolated-tier registration got no egress and every tool reported "could not reach the API". Add `mint.yaml` to `files`, add it to `.mcpbignore` (it belongs in the npm tarball, not the `.mcpb`), and assert `pkg.files` includes it in `tests/packaging.test.ts`. A `--github` registration reads the tree and is unaffected — which is exactly why this hides from anyone who tested hosting that way.

**Keep it true as the MCP changes.** mcp-host's nightly check reads the manifest at each registration's newest version and alerts its owner when a published version asks for something the registration does not supply. A stale `mint.yaml` therefore either cries wolf or stays silent when it should not — updating it is part of shipping a change that needs a new variable, a new dependency, or persistence.

### Is this MCP hostable? — check the repo, don't recite this list

**Read `~/git/mcp-host/docs/BROWSER-BRIDGE.md` before answering "can this be hosted".** This section asserted "browser-bridge: not implemented" for months after it stopped being true, and an agent repeated that to the user while sixteen bridged registrations were live. The auth question below is still the right question; its answers move.

**Why that keeps happening, mechanically: the copy of this skill in your context is a snapshot, and the file is a symlink into a live worktree.** `~/.claude/skills/mcp-fleet-builder/SKILL.md` symlinks to this file, so a merge — or another session editing it — changes the skill *underneath a running session*, while the version loaded into context stays frozen at session start. Diffing the two locations will NOT reveal this: they are the same inode. It happened again during the thumbtack-mcp build — the context copy still said bridges could not be hosted, and that was repeated to the user three times before anyone opened the file. So for any claim about **capability** (what can be hosted, which fpx verbs exist, which mcp-utils helpers are available) — `cat` the section, or interrogate the artifact itself (`fpx` with no args, `mcp-host` with no args, the package's `.d.ts`) — before asserting it. Treat this document as a pointer to the truth, not the truth.

**And when you interrogate the artifact, read `origin/main` — a LOCAL CLONE IS AN ARTIFACT WITH ITS OWN STALENESS.** "Go look at the code" is only half the rule; a `~/git/<repo>` working tree can be behind, ahead, or on a feature branch, and it answers with total confidence either way. This bit during the alphaportal-mcp build: the local `~/git/mcp-host` clone was 3 commits behind and still carried `HOSTING_MANIFEST_FILE = 'mcp-host.yaml'` from before the rename, so grepping it "proved" the fleet's `mint.yaml` convention was wrong and every manifest silently ignored — a false alarm raised to the user before `git show origin/main:…` showed `MINT_MANIFEST_FILE = 'mint.yaml'` with `mcp-host.yaml` kept only as a legacy alias. So: `git fetch` first, then read through the ref (`git show origin/main:path/to/file`, `git ls-tree -r --name-only origin/main`) rather than opening the working copy — and check `git rev-list --count HEAD..origin/main` before trusting anything a local tree told you. A renamed file makes this especially treacherous, because the stale path still exists and still parses.

- ✅ **bearer / API-key** (splitwise, setlist, musicbrainz, flightaware) — the simplest case.
- ✅ **username/password with a real server-side login** (ofw). Store the credentials as secrets so the child can re-login when its token expires.
- ✅ **username/password + MFA**, *provided the refresh token skips MFA* (kiaaccess). Bootstrap locally, then store the refresh token as a secret. If MFA cannot be skipped, every session needs a human and hosting is pointless — test this explicitly and early.
- ✅ **fetchproxy / browser-bridge** — built as of fetchproxy 2.1.0, and in routine use. See below.
- ❌ **ephemeral session-cookie writes with no server-side re-login.** Mixed repo → register with `--tools a,b,c` to serve only the serverless-safe subset. That flag narrows the whole connector, not just the tool menu: while it is set, `prompts/list` and `resources/list` come back empty and the handshake stops advertising those capabilities, so a capability exposed twice cannot be reached through the second door.

### Browser-bridge MCPs CAN be hosted (fetchproxy 2.1.0+)

The extension dials a configured `wss://` target; the gateway parks the browser's socket in a `BridgeRoom` Durable Object **per account**; the runner runs one agent per bridged child, dialling that child's loopback port in the extension role. fetchproxy's crypto is end-to-end (per-MCP AES-256-GCM from its own X25519 identity), so mcp-host carries the traffic **without being able to read it** — the security property that made this tractable at all.

A bridged registration requires ALL of:

- `runtime: fly-shared` — the bridge agent dials the child's loopback port on the machine it runs on.
- **`dataDir: true`** — a fetchproxy identity lives at `$HOME/.fetchproxy/identity/<name>.json` and the pair code derives from it. Without persistence every cold start mints a fresh identity and re-prompts pairing in the user's browser — on a scale-to-zero machine, constantly. The API refuses `bridge` without it.
- `bridge: true` and `bridgePortEnv: '<SVC>_WS_PORT'` — naming a port env without `bridge` is refused rather than silently dropped.

**The CLI has no `--bridge` flag.** `register` supports `--data-dir` but not the bridge fields, so set those over the control API — and the route is **`PUT`** on the registration **id**. `PATCH` 404s; addressing by slug 404s.

```sh
mcp-host register --slug angi --npm '@chrischall/angi-mcp@0.1.0' --data-dir
mcp-host list            # grab the reg_… id for the slug
curl -X PUT "$MCP_HOST_URL/api/v1/registrations/<reg_id>" \
  -H "authorization: Bearer $MCP_HOST_ADMIN_TOKEN" -H 'content-type: application/json' \
  -d '{"bridge":true,"bridgePortEnv":"ANGI_WS_PORT"}'
mcp-host bridge new "<browser name>"   # one credential per browser, account-scoped
mcp-host bridge ls                     # a live lastUsedAt means a browser is already attached
```

**Verify by log, not by exit code.** After `prewarm`, the child's stderr should show `listening on 127.0.0.1:<port>` with a **per-registration port, not 37149** — that is the runner injecting `<SVC>_WS_PORT`, and it only works because the MCP resolves its port through `readPortEnv`. A 200 from the PUT proves the row changed, not that the bridge works.

**Make every new bridge repo hosting-ready — it is now load-bearing, not speculative.** Take the concentrator port from `readPortEnv('<SVC>_WS_PORT', 37149)`. honeybook is the one repo that cannot: it is a `@fetchproxy/bootstrap` consumer and never names a port, so **prefer an explicit transport over the bootstrap helper** in any new bridge repo. (fetchproxy 2.1.0 added a `FETCHPROXY_WS_PORT` fallback, which is the only way to reach the bootstrap path.)

**State the caveat when offering this.** `BROWSER-BRIDGE.md` calls itself *"built, and unproven over the WAN"*: step 6 — keepalive margin over a real round-trip, and a Fly machine reaching `stopped` with a browser attached — is still answered only on a laptop. Offer hosting, but say that part out loud. Note also that any tool NOT needing the bridge (a taxonomy read from public sitemaps, a local calculator) works through the connector regardless of bridge health, which is worth telling the user.

### What actually differs from the Worker era

- **There IS a filesystem** — but it is the *runner's*, not the user's. `dataDir: true` gives the registration a `$HOME` that survives restarts (needed for anything that persists identity, tokens or a cache). What still does not work is a tool that writes a file **for the user to open**: the path it returns is on a Fly machine they cannot reach. Keep the injectable IO boundary (ofw's `AttachmentIO`, artsonia's `DownloadIO`) so stdio writes to disk and the hosted path returns bytes inline — and give the IO a `persistsFiles` flag so a tool does not report `wrote <path>` for a file the user will never see. Cap cumulative inline bytes and note what was dropped rather than silently truncating.
- **Secrets: use `--secret-env`, never `--env`.** `--env` values are stored as plaintext literals and echoed by every registration GET. The control API warns (by NAME only) when a literal looks secret-shaped — `*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*APIKEY*` anywhere, `KEY`/`PAT` as whole words — but it does not refuse the registration.
- **Versions are pinned at registration.** An npm tag or bare name resolves to an exact version + integrity hash; upgrades are explicit (`updatePolicy`). A `--github owner/repo#ref` source pins to a commit, and installs never run package scripts unless you pass `--build`.
- **Deploy is not per-MCP.** `mcp-host` itself is deployed once (`docs/DEPLOY.md`). Registering an MCP needs no Cloudflare account, no API token, no KV namespace, and no custom domain.
- The whole class of Cloudflare startup traps is **gone**: the `.env` module-init guard, the pure-constructor rule for module-singleton clients, and the detached `globalThis.fetch` binding error were all `workerd` behaviours. The child runs on Node, so Node semantics apply.

### Gotchas that survive

- **A green job does not mean the action happened.** Registration prewarms the runner (fetch + install) so the first tool call does not wait on npm — but verify the artifact, not the exit code — and note **`status` / `logs` / `prewarm` / `restart` take the registration ID, not the slug** (`mcp-host status thumbtack` → `HTTP 404: no registration thumbtack`; use `reg_…`, which `mcp-host list` prints). The check that actually proves the server booted is `.instance`: `state: "ready"` with your own banner in `lastStderr`. Then a real tool call through the connector — an unauthenticated `POST` to the connectUrl returning `401` + `WWW-Authenticate: Bearer realm="OAuth"` confirms the endpoint is live and enforcing auth.
- **Publish before you register.** An npm-sourced registration resolves against the registry, so the version must actually be published — see the "a green tag does not mean a green publish" rule; confirm with `npm view <pkg> version` first.
- **Auto-merge orphans your follow-up commit.** Less acute now that hosting is not a chain of small PRs, but a repo change made *for* hosting (a `*_WS_PORT` env var, an injectable IO) is still one complete PR, not a staging branch.

## Conventions (how chris likes them)

- **TDD, always.** Failing test → minimal code → green. Especially for write tools.
- **Verify endpoints before building them — at the right layer.** For no-API sites, capture the real request (DevTools → Network → "Copy as cURL", or a HAR) and pin the request *shape* in `docs/<SERVICE>-API.md`. Never code a write against an assumed body, and never encode a gate field you haven't seen succeed: confirm an actual successful artifact end-to-end (a real file/row), because downloads and navigations don't show up in XHR/`fetch`/HAR. Extract only the shape — **never commit captured cookies/tokens/signatures** (secret-scan before committing). **Premium APIs need a funded account to verify** — image/LLM endpoints (gemini-mcp's `gemini-3-pro-image`) return `429 … free_tier_requests, limit: 0` on a free key, so the verification gate is BLOCKED until the human enables billing; surface that and wait rather than guessing the shape. Also pin the SUCCESS response from a real 200 — request and response casing can differ (Gemini accepts snake_case `inline_data` on the request but returns camelCase `inlineData`), and a model/endpoint may only exist on `v1beta`, not `v1`. **Re-verify for EVERY new knob and especially every new/Beta endpoint, not just the first build** — a doc scrape (and a WebFetch summarized by a small model) is frequently wrong or incomplete: confirm each field name, accepted enum values, required headers (the Gemini Interactions API needs `Api-Revision: 2026-05-20`), and output constraints (it only accepts `image/jpeg`, not png) with a real call before coding. Cheap knobs (a new `imageSize` value, `thinkingConfig`, `seed`) are one curl each; a whole new endpoint earns a full request+response capture pinned in `docs/<SERVICE>-API.md`. **Sibling endpoints can use DIFFERENT input grammars — don't assume they share one:** AeroAPI's `/flights/search` + `/search/count` take a simplified `-key value` string, while `/search/advanced` + `/search/positions` take a structured `{op key value}` one (and the field names differ — `orig`/`dest`, not `origin`); mixing them `400`s. **Live-verify through the BUILT client, not just raw curl** — a throwaway read-only probe that `import`s `dist/client.js` and calls each tool's path exercises the real path-building + cache + error layers end-to-end (it caught the wrong-grammar example a mocked unit test never would), and it confirms tier-gated endpoints `401` gracefully. **Space the probe calls** (~3–4s apart): a billed/rate-limited API will `429` a burst of a dozen and mask the real results.
- **A documented OpenAPI/Swagger API on a site is often a SELLER/partner surface you can't actually use — find the CONSUMER surface before committing to an archetype.** Many portals (ticketing, real-estate, school) publish a clean REST API (e.g. `api.<svc>.com/v3` with a Swagger UI → `openapi.json`) that turns out to require **OAuth2 client-credentials / password-grant with venue/partner credentials a consumer doesn't have** — every endpoint 401s, even the ones labelled `/public/*`. The data a consumer can actually reach lives on the **www site's own internal API** (`/api/online/...`), which is typically **bot-walled** (DataDome/PerimeterX → fetchproxy) AND may return **encrypted/opaque payloads on its richest endpoints** (etix's full-text `/search` came back as base64 blobs; only the lighter `search/suggest` was clean JSON, and detail pages were SSR HTML w/ schema.org JSON-LD + microdata). So before picking bearer-vs-fetchproxy: probe BOTH the documented API (is it consumer-authable, or seller-only?) and the consumer site (reachable server-side, or walled? clean JSON, or encrypted/SSR?), and when the two diverge, **ask the user which surface they want** — a seller box-office MCP and a consumer-discovery MCP share almost no code (etix: confirmed seller-`v3`-OAuth vs. consumer-fetchproxy was a one-question fork that decided the whole build).
- **Never match schema.org JSON-LD by `@type` — match by SHAPE.** Sites emit the *specific* subtype, not the generic one: a Thumbtack plumber's business node is `"@type":"Plumber"`, an electrician's is `"Electrician"`, and only some trades are literally `"LocalBusiness"`. `findJsonLdEntity(html, 'LocalBusiness')` therefore returns `null` for most pages, and the failure is **silent** — an empty summary, not an error. Select the node by the fields you actually read (a `name` plus an `aggregateRating` or `address`), and take `@graph[0]` positionally in a `jq` recipe rather than filtering on the type. Nothing catches this but a live probe: fixtures captured from one page type will happily agree with the wrong predicate forever (thumbtack's fixture was a house cleaner — the one trade that *is* `LocalBusiness`).
- **Confirm-gated writes.** Every mutating tool takes `confirm` (`schemaConfirm` from `zod`). Without `confirm: true` it makes **no** network call and returns a dry-run `preview()` of exactly what would be sent. Route every mutation through one private `client.write()` that attaches auth (cookie/CSRF or bearer) centrally.
- **Stream file uploads.** Never `readFileSync` a file just to wrap it in `new Blob([buf])` — use `fileBlob` / `readFileHead` from `@chrischall/mcp-utils` (or `fs.openAsBlob` directly) so a 20 MB upload isn't a 20 MB heap buffer.
- **Results:** `textResult(data)` for everything; errors via the typed `McpToolError` subclasses with an actionable `hint`.
- **Compact projection + drift-fallback for verbose reverse-engineered listings.** A reverse-engineered listing/detail endpoint often returns ~100 fat records — a lot of context for an agent that just wants to browse or rank. Add an opt-in `compact` arg that projects each item to a slim summary keyed off **documented** fields only, deriving convenience fields locally (e.g. metric→imperial) so the agent needn't convert. Validate the envelope with a **loose** zod schema that covers only the fields you read; when the expected array/shape isn't present, **warn to stderr and return the RAW response** rather than an empty/wrong projection — undocumented APIs drift, so degrade, never break. Keep `compact` default `false` so full records stay reachable. (alltrails-mcp.)
- **Flipping a verification/status claim is a TREE-WIDE edit, not a file edit.** A "this endpoint is unverified" claim propagates into prose, a spec constant, tool descriptions, dry-run previews, result payloads, test assertions AND test *titles*. Three consecutive review rounds on kiaaccess each caught the same defect in a different file because each fix grepped one file. `grep -rniE "verified|unverified|exercised against" README.md docs/ skills/ src/` and read every hit — one full sweep is strictly cheaper than three targeted ones. Related: **test fixtures must DERIVE such flags from the real spec**, never hardcode them — a fixture defaulting to `verified: false` happily asserted `false` for endpoints that had been verified, and the tests passed.
- **Fixing a doc inaccuracy by INVERTING it is still an inaccuracy — go re-read the code.** A reviewer says "X does not fall back to Y"; the tempting one-line fix is to assert the opposite, and it fails the next round. gogcli's `GOG_TIMEZONE`/`DISPLAY_TZ` help was wrong three ways across two rounds: first `DISPLAY_TZ` was described as depending on `GOG_TIMEZONE` (backwards), then the correction claimed "neither reads the other" (also false — `naiveSourceTimeZone()` really does fall back to `displayTimeZone()`). The relationship was directional the whole time, and only opening `timestamps.ts` settled it. When a review flags a factual claim, read the function and describe what it does, naming it; do not negotiate with the reviewer's sentence.
- **Secrets:** `.env` gitignored; throwaway-test writes go only to blackholed addresses (`@example.com`); only the user's own account/data. **`truncateErrorMessage`/`redactSecrets` match secret SHAPES — Bearer, JWT, `sk-`, `ghp_` — so they do NOT catch a password, a 6-digit OTP, or an opaque refresh token, none of which have a recognisable shape.** Any error path that renders an upstream body to a user (a connector login page especially) must additionally scrub the literal values it just sent: `raw.split(secret).join('[redacted]')` for each. Guard the empty needle — `split('')` splices the placeholder between every character. kiaaccess rendered `userCredential.password=<the real password>` onto its login page while "sanitizing" through `truncateErrorMessage`, and both the author and the reviewer assumed that was enough.
- **A test written to confirm a fix is the cheapest place to discover the fix was insufficient — so write it to assert the OUTCOME, not the mechanism.** Asserting "the call is now wrapped in the sanitizer" would have passed while the password still leaked; asserting "the rendered message does not contain the password" failed and exposed that the sanitizer never matched it. Same shape as the false-green traps under *Verifying a write actually landed*: state the property you actually care about and let it fail.
- **Never merge PRs or add `ready-to-merge` yourself.** Squash-merge is the default; `pr-auto-review` + `auto-merge` ship it. On a `warn`/`fail` verdict, surface the findings and ask — don't override.
- **Describe what it does, neutrally.** Public descriptions (`marketplace.json` `metadata.description`, `server.json`, the GitHub repo About) state the *mechanism* — e.g. "routes through the user's signed-in `<site>` tab via the fetchproxy bridge, reusing their authenticated session" — not bot-evasion framing ("to dodge bot detection"). Same factual tone as CLAUDE.md's "every request rides the user's own browser session."

## Repo bootstrap — git, labels, release-please

A new fleet repo isn't done until ALL of this exists. Each line below was a real failure when missing (CI red, review step erroring, `main` unprotected, bundle bloat).

**Workflows** (`.github/workflows/`): the fleet uses **thin stubs that call the shared reusable workflows in [`chrischall/workflows`](https://github.com/chrischall/workflows)** — `ci.yml` → `reusable-mcp-ci.yml@main`, `pr-auto-review.yml` → `reusable-pr-auto-review.yml@main`, `auto-merge.yml` → `reusable-auto-merge.yml@main`; `release-please.yml` runs `release-please-action` then the `chrischall/workflows/.github/actions/mcp-publish@main` composite (npm `--provenance` + `.mcpb` + MCP registry + ClawHub — it **derives the package/skill name from the repo**, `package-name` defaults to the repo name, so NO hardcoded `skill_name`/`.mcpb` filename/`install-mcp-publisher` pin); `claude.yml` (`@claude` dispatch) stays inline; plus `dependabot.yml`. **Node:** `node-version: "26"`. **COPY THE STUBS FROM A FRESHLY-UPDATED SIBLING'S `origin/main`, NOT a local working tree** (`gh api repos/chrischall/<sibling>/contents/.github/workflows/<f>.yml --jq .content | base64 -d`) — a local clone can be STALE and hand you the OLD self-contained workflows (still work, but drift from the fleet, and dependabot then opens bumps for pinned actions the stubs no longer reference). The stubs are repo-agnostic — drop them in verbatim (node 26, `npm run build`/`npm test`, empty `conventions_hint`). The stub's job appears as `ci / ci`, but the required check is the `ci-gated` status either way (see the ruleset note below). **Register the new repo in `chrischall/workflows/fleet.json`** (just `{"repo": "chrischall/<name>"}` — defaults apply; override only `pat_secret`/`ci`/`node_version`/`test_command` per repo) so fleet-wide rollouts (`scripts/rollout.sh`, stub-trigger sweeps) include it — a brand-new repo is easy to forget there, and then it silently misses every later fleet change.

**Labels** — per-repo (`chrischall` is a *User* account: no org-wide labels/secrets). Create `auto-review`, `ready-to-merge`, `review-with-opus`, `release-ready` (the shared `reusable-pr-auto-review` gates the release-please PR's review on this — missing it just means the release PR never auto-reviews), `autorelease: pending`, `autorelease: tagged`, plus dependabot categories (`ci`, `security`, `test`, `javascript`, `github_actions`, `ignore-for-release`). Missing `auto-review`/`ready-to-merge` → pr-auto-review's first step (`gh pr edit --add-label auto-review`) errors and arming can't happen.

**Order matters: genesis push FIRST, rulesets SECOND.** A ruleset requiring a PR on `~DEFAULT_BRANCH` blocks the very push that puts the workflows on the default branch, and weakening protection to escape is (rightly) the kind of thing that gets refused. Two related facts about a brand-new empty repo: it has **no default branch at all** until the first push, so a PR into `main` fails with *"Base ref must be a branch"*; and **whatever branch you push first BECOMES the default**. If you have already created the rulesets, that second fact is the escape hatch — push a throwaway branch (it becomes default, so `main` is unguarded), push `main`, repoint the default with `gh api -X PATCH … -f default_branch=main`, then delete the throwaway. Cleaner still: create the repo, push `main`, *then* apply rulesets.

**Branch protection** — two rulesets on `~DEFAULT_BRANCH` (personal account uses rulesets, not classic protection): (1) block `deletion` + `non_fast_forward`; (2) require a PR + the required check, which is the **`ci-gated` COMMIT STATUS — a status context, not a job name.** (Verified across the fleet 2026-07-19: every live ruleset requires `ci-gated`.) Getting this wrong is silent and total — a ruleset requiring a context that nothing posts blocks every PR forever — so copy `ci-gated` verbatim and never put a job name here.

**Two shapes of `ci.yml` both post `ci-gated`**, so don't infer the gate from the workflow's shape: (a) the thin stub calling `reusable-mcp-ci.yml` with `gate-mode: status`, whose job shows up as `ci / ci`; (b) a self-contained `ci.yml` running the `chrischall/workflows/.github/actions/arm-gate@main` composite in status mode, whose job shows up as a bare `ci` (mcp-utils, realty-mcp, apple-swift-mcp, curtaincall, …). Both are current and correct — the job name is incidental, only the `ci-gated` status is required. Either way the caller must grant `permissions: statuses: write`, or the gate cannot post at all.

**How the status gate behaves:** un-armed PR → the gate posts **`ci-gated: pending`** (yellow) while the job itself stays green; once `pr-auto-review` passes and arms `ready-to-merge`, that `labeled` event fires the real CI run, which flips `ci-gated` to success. Dependabot PRs run CI unconditionally. **This is strictly stronger than the legacy gate it replaced:** that one left `ci / ci` *skipped* on an un-armed PR, and GitHub treats a skipped required check as **satisfied**, so an admin could click Merge before CI had ever run. A *pending* status is not satisfied, so status mode blocks the button too — the old "convention, not enforcement" caveat is now closed. **But `gate-mode` still defaults to `fail` (legacy) in `reusable-mcp-ci.yml`**, and the `ci-gated` step is conditional on `gate-mode == 'status'`, so a stub that omits the input posts no status at all. Pair the input and the ruleset context, or the repo is bricked.

**Repo setting: Allow auto-merge** — turn it on (`gh api -X PATCH repos/chrischall/<repo> -F allow_auto_merge=true`). This is separate from the workflow and the ruleset, and easy to miss: with it OFF, `auto-merge.yml`'s `gh pr merge --auto` silently fails to arm, so Dependabot / `ready-to-merge` PRs sit OPEN forever even with green CI. The workflow + `RELEASE_PAT` + the `ci-gated` ruleset are all necessary but NOT sufficient without this toggle. (Check the fleet: `gh api repos/chrischall/<repo> --jq .allow_auto_merge`.) **The ruleset makes this toggle load-bearing — applying protection LATER breaks a previously "working" repo:** before the `ci-gated` ruleset exists, armed PRs can merge without the toggle (no required checks pending → the pipeline's merge path succeeds), so the gap hides. The moment `update-ruleset.sh` lands, the next armed PR's arm step fails `GraphQL: Auto merge is not allowed for this repository (enablePullRequestAutoMerge)` and the PR sits green-but-open. Recovery needs NO new PR event (unlike the review step): enable the toggle, then `gh run rerun <failed-auto-merge-run-id> --failed` — the arm step re-executes `gh pr merge --auto` fine on a rerun and merges immediately when checks are already green. Apply ruleset + toggle together; a repo's `update-ruleset.sh` should set `allow_auto_merge=true` alongside the squash-only merge policy so the pair can't drift apart.

**Repo setting: squash title = PR_TITLE** — set `squash_merge_commit_title=PR_TITLE` (+ `squash_merge_commit_message=PR_BODY`) alongside the merge policy: `gh api -X PATCH repos/chrischall/<repo> -F allow_auto_merge=true -F allow_squash_merge=true -F allow_merge_commit=false -F allow_rebase_merge=false -F delete_branch_on_merge=true -f squash_merge_commit_title=PR_TITLE -f squash_merge_commit_message=PR_BODY`. This **closes the single-commit-PR trap** documented under *the PR title is the release decision*: with the default, GitHub squashes a one-commit PR using the COMMIT subject, which is how encore-ios #39 shipped an unintended major bump. Setting it explicitly makes the PR title authoritative in every case.

**Don't trust a sibling's `scripts/update-ruleset.sh` — check the context it writes before running it.** Only a few repos carry the script, and copies drift from the rulesets they configure: as of 2026-07-19 `alltrails-mcp` and `getyourguide-mcp` both shipped a copy still writing `"context": "ci / ci"` while their own live rulesets were correctly on `ci-gated`. Running such a copy *breaks a working repo* — it replaces the required check with one nothing reports, blocking every PR. Grep the script for `required_status_checks` and confirm it says `ci-gated` before executing it or copying it into a new repo.

**Order note: Dependabot opens PRs within minutes of the genesis push — usually BEFORE the human has set the secrets.** Those PRs get green CI but their arm step fails with an empty `GH_TOKEN` (`gh: To use GitHub CLI in a GitHub Actions workflow, set the GH_TOKEN environment variable` → `auto-merge arm failed (PR state=UNKNOWN)`), because `auto-merge.yml` passes `release_pat: ${{ secrets.RELEASE_PAT }}` and the secret did not exist yet. The wiring is fine; only the timing was wrong. Recovery is `gh run rerun <arm-run-id> --failed` per PR once the secrets exist — no new PR event needed. Expect them to then merge **serially with rebases**, since they all touch `package-lock.json` and go `DIRTY` behind each other; `@dependabot rebase` nudges a stuck one. Per the never-merge rule, arming these is the human's call — ask first.

**Secrets** — per-repo, set by the **human** (an agent must never set credential values): `CLAUDE_CODE_OAUTH_TOKEN` (review), `RELEASE_PAT` (release-please + the auto-merge/arm step — a `GITHUB_TOKEN`-added label won't fire downstream workflows), optional `CLAWHUB_TOKEN`; plus npm **trusted publishing** for the `--provenance` publish.

**Claude GitHub App — install on the new repo (separate from the secrets).** `pr-auto-review.yml` posts its verdict as `claude[bot]` via the App's OIDC, and the **arm step reads that verdict to add `ready-to-merge`**. If the App isn't installed on the repo, the review job still runs and exits `success` but posts NOTHING and emits no `structured_output` — so the arm step reads `verdict=unknown` and never arms (PR sits green-but-open forever). The `CLAUDE_CODE_OAUTH_TOKEN` only authenticates the model, not repo posting. Human step: github.com/apps/claude → Configure → add the repo. Tell: zero `claude` PR comments = App not installed.

**release-please** — `release-please-config.json` (`package-name`, `release-type: node`, `changelog-sections`, `extra-files`) + `.release-please-manifest.json`. The workflow itself is the thin stub above (`release-please-action` → `mcp-publish` composite); the publish job stays in *this* repo's `release-please.yml` (not a reusable workflow) because npm trusted publishing + `mcp-publisher` bind to this repo's workflow identity via OIDC. **`extra-files` MUST list every file that carries the version**, or `versionSyncTest` fails the release PR's CI: `manifest.json` `$.version`; `server.json` `$.version` + `$.packages[*].version`; `.claude-plugin/plugin.json` `$.version`; `.claude-plugin/marketplace.json` `$.plugins[*].version` + `$.metadata.version`; and **every `src/*.ts` with an `// x-release-please-version` marker**. **Prefer a single `src/version.ts`** (`export const VERSION = '…'; // x-release-please-version`) imported everywhere it's needed — one source, one extra-files entry, nothing to forget — rather than scattering the marker across `index.ts` + a `SERVER_VERSION` in `auth.ts`. Don't hand-bump; release-please does it. **Seed `.release-please-manifest.json` at `0.0.0` on a brand-new package AND set `initial-version`** — seeding a natural-looking `0.1.0` makes the first `feat:` bump to `v0.2.0`, so the first tag skips `v0.1.0` entirely (release-please treats the seed as "already released"). But `0.0.0` alone does **NOT** yield `0.1.0`: with no prior tag, release-please applies its initial-release default and proposes **`1.0.0`** (observed on charlotteonthecheap-mcp 2026-07-19 — the genesis `feat:` produced a `chore(main): release 1.0.0` PR). A brand-new server shipping as 1.0.0 advertises a stable API it has not earned, and the rest of the fleet is on 0.x. So pair the `0.0.0` seed with **`"initial-version": "0.1.0"`** in `release-please-config.json`, and add **`"bump-minor-pre-major": true`** so a later breaking change on 0.x bumps the minor instead of silently declaring 1.0.0. Check the proposed version on the first release PR before merging it — that PR is the last chance to correct it without a bogus tag.

**Genesis race: release-please fires on the first push and fails `Input required and not supplied: token` if the secrets land seconds later.** Harmless and NOT a config error — the workflow ran before `RELEASE_PAT` existed. `gh run rerun <id>` once the secret is set produces the release PR normally. Don't go debugging the config for this.

**`package.json` must declare `repository`** — `{"type":"git","url":"git+https://github.com/chrischall/<repo>.git"}`. `npm publish --provenance` validates the sigstore bundle against it and rejects the whole publish with **`npm error code E422 … Error verifying sigstore provenance bundle: Failed to validate repository information: package.json: "repository.url" is "", expected to match "https://github.com/chrischall/<repo>" from provenance`**. This fires AFTER release-please has already tagged and cut the GitHub Release, so the release looks green while npm never moves and the registry / ClawHub / release-artifact steps are all silently skipped (thumbtack v0.1.0). **Re-running the failed job cannot fix it** — the tag's tree still lacks the field, so it fails identically; per "release-please owns versions", ship a `fix:` and let the next patch publish. Copying a sibling's `package.json` gets this for free; writing one from scratch does not. Guard it with a `tests/packaging.test.ts` asserting `repository.url`, the scoped name + `publishConfig.access`, and `files` including `skills` — all things that otherwise only fail once a tag exists. Cheapest possible pre-flight: `npm publish --dry-run --provenance --access public` from the release branch's tree.

**Publish scaffold** (also list in package.json `files`): `manifest.json` (mcpb; `runtimes.node` floor stays at an **LTS** like `>=22.5`, not 26, so LTS users install), `server.json` (registry; description **≤ 100 chars** or `mcp-publisher` 422s), `.claude-plugin/plugin.json` + `marketplace.json`, `.mcp.json`, `skills/<name>/SKILL.md`, and **`.mcpbignore`** so `mcpb pack` ships only `dist/bundle.js` + `manifest.json` + `package.json` — exclude `src/`, `tests/`, `docs/`, `node_modules/`, `.env*`, the registry/plugin manifests, **and** `release-please-config.json` / `.release-please-manifest.json` / `CHANGELOG.md`.

**mcp-publisher** — install via the shared pinned, SHA-256-verified action `chrischall/workflows/.github/actions/install-mcp-publisher@main`, NOT the upstream `releases/latest | tar xz` (that binary runs with the OIDC + RELEASE_PAT + CLAWHUB tokens).

## Gotchas (hard-won)

- **ESM + NodeNext**: every relative import ends in `.js`, even from `.ts`.
- **An injectable `fetchImpl` default must be a receiver-safe WRAPPER, not the bare global `fetch`.** Storing `this.fetchImpl = opts.fetchImpl ?? fetch` and later calling `this.fetchImpl(...)` invokes `fetch` with `this` bound to your client instance; **older undici (Node 18–20, which several MCP hosts — Claude Desktop included — still bundle) throws `TypeError: Illegal invocation` for any receiver that isn't `globalThis`**, and Node 26 tolerates it — so this is invisible in local dev and only bites a user on an older host. The throw lands in whatever `catch` wraps the call and masquerades as something else: alphaportal-mcp reported "token refresh could not reach the API" (a network-failure message) for what was actually a mis-bound fetch. Default to `opts.fetchImpl ?? ((input, init) => fetch(input, init))`, and pass that same wrapper to `createApiClient({ fetchImpl })`. (Distinct from the *workerd* `globalThis.fetch` binding trap under §*What actually differs from the Worker era*, which really is gone on Node — this is a live Node-side variant.) While you're there, surface `err.cause?.code` + the endpoint in reach-failure messages, so a genuine DNS/TLS/egress block is diagnosable instead of opaque.
- **`"types": ["node"]`**: NodeNext repos need this in `tsconfig.compilerOptions` once they import a scoped pkg like `@chrischall/mcp-utils`, or `tsc` fails with `Cannot find name 'path'/'url'`. Add `types`, not `typeRoots`.
- **`tsconfig rootDir: "src"`** (not `"."`): with `rootDir:"."` + `include:["src"]`, `tsc` emits `dist/src/index.js` while `package.json` `bin` points at `dist/index.js`, so `npx <svc>` (and any host launching the bin) can't find its entry. Copying a sibling's tsconfig avoids this; a fresh scaffold gets it wrong.
- **The `.mcpb` bundle ships NO `node_modules` — an eager import of an esbuild-`--external` dep crashes it at LOAD.** A top-level `import { X } from 'pkg'` of an externalized/optional dep (e.g. `@fetchproxy/server` in `transport-fetchproxy.ts`) throws `ERR_MODULE_NOT_FOUND` the moment the host spawns the bundled server — before it answers `initialize` (the host logs "Server transport closed unexpectedly", not a useful error). Make optional/externalized deps **lazy**: `import type { X } from 'pkg'` (type-only, erased) + `const { X } = await import('pkg')` inside the method that needs it, so the default path never touches it. `loadDotenvSafely`'s guarded import already does this for `dotenv`; do the same for `@fetchproxy/server` in any cookie-session/bearer repo that keeps fetchproxy as an optional fallback.
- **Add a server-boot smoke test** (`tests/server-boot.test.ts`): spawn the REAL built artifacts — `dist/bundle.js` in a temp dir with NO `node_modules` (the `.mcpb` runtime) and the `bin` `dist/index.js` WITH them — run the `initialize` + `tools/list` handshake, and assert the tools list. Catches both the eager-import crash above and a wrong `bin` path, which unit tests (mocking everything) never see. **Assert `tools.length >= N`, not an exact count** — PR CI runs the branch MERGED with `main`, so a hardcoded `toHaveLength` breaks the instant another PR adds a tool; let `index.test.ts` own the exact roster on its own branch.
- **Dependabot splits peer-locked pairs and BOTH halves fail CI — group `vitest` explicitly.** `vitest` and `@vitest/coverage-v8` peer-depend on each other at an **exact** version, so bumping either alone makes the peer set unsatisfiable and `npm ci` dies. The stock `dev-dependencies` group only covers `minor`/`patch`, so a **major** escapes it and arrives as two separate, individually-red PRs. Re-running their arm jobs cannot help — the CI failure is real. Fix: add a `vitest` group with `patterns: ["vitest", "@vitest/*"]` and `update-types: [major, minor, patch]`, **listed first** (first matching group wins), then supersede the split PRs with one that bumps both. Every repo in the fleet is exposed to this.
- **vitest 4 counts branches more strictly than 3.x — expect a 100%-threshold repo to go red on upgrade.** That is the tool getting *more* accurate, not a regression: on thumbtack it dropped coverage to 99.3% and pointed at a genuinely untested `x !== null` guard that vitest 3 had never counted. Cover the branch; don't lower the threshold.
- **`npm test` is not the CI command in every repo — read `test-command:` in `ci.yml` before saying "tests pass".** Roughly a third of the fleet (15 repos as of 2026-08-25: accessoticketing, alltrails, booli, evite, getyourguide, hemnet, housecallpro, jobber, kiaaccess, ofw, pickuppatrol, schoolpass, sixflags, skylight, thumbtack) runs **`npm run test:coverage`**, which enforces the 100% branch threshold above. `npm test` passes while `test:coverage` fails, and nothing local surfaces the gap — schoolpass-mcp #8 went out with 110/110 green and failed CI at 99.07%. **The usual culprit is a ternary in a MESSAGE, not in logic**: a `hint` reading ``cond ? 'do X' : 'do Y'``, or ``x != null ? ' and x' : ''``, is a real branch to v8, and a test suite naturally exercises only the arm it happens to trigger. Run the repo's own command, and when you add a hint that varies, add the case that hits the other arm.
- **zod 4**: mcp-utils peer-requires `zod@^4.4.0`. Repos still on zod 3 must bump (schemas are compatible; `z.string().email()` is deprecated-but-works).
- **Never commit secrets**: `.env` must be gitignored. Real creds live in `.env` (local) or the MCP host's `mcp_config.env`. If `.env` is tracked, `git rm --cached` it.
- **`.gitignore` must list `coverage/`** (alongside `dist/`, `node_modules/`, `.env*`, `*.tsbuildinfo`). The minimal `.gitignore` copied across the fleet often omits `coverage/`, so the moment you run `npm run test:coverage` + `git add -A` you silently stage the whole HTML report. The genesis leak-check catches it, but add `coverage/` at scaffold time so it never happens. (`.mcpbignore` already excludes it from the bundle — that's separate from git tracking.)
- **Version sync**: version is duplicated across `package.json`, `src/version.ts` (`x-release-please-version` marker), `manifest.json`, `server.json`, `.claude-plugin/*`. Keep them equal — `versionSyncTest` from `/test` guards it. Don't hand-bump; release-please / the Tag-&-Bump action does it. **`versionSyncTest` flags EVERY line containing the literal `x-release-please-version` — including PROSE.** If a doc comment near `version.ts` mentions the marker string in passing (e.g. "tracked via the `x-release-please-version` marker"), the test reads that line, finds no version literal, and fails with `<no version literal found>`. Keep the marker string off every line except the actual `export const VERSION = '…'; // x-release-please-version` line — reword explanatory comments to not quote it.
- **`server.json` description ≤ 100 chars** (MCP registry schema) — over that, `mcp-publisher publish` 422s.
- **Private repo + npm provenance don't mix.** `npm publish --provenance` (the fleet default — sigstore attestation) only works from a **public** GitHub repo. A private repo 422s at the npm step: *"Unsupported GitHub Actions source repository visibility: 'private'. Only public source repositories are supported when publishing with provenance."* So for a private / personal MCP, pick one: (a) keep it unpublished — `"private": true` in `package.json` + remove the `publish` job from `release-please.yml` (release-please can still own version bumps + tags + the `.mcpb`/GitHub release), (b) drop `--provenance` from the `npm publish` step (you lose the attestation; a public *scope* still publishes fine via `--access public`), or (c) make the repo public. Don't leave the default `--provenance` publish wired on a private repo — every release fails.
- **npm name: check it FIRST, and scope when it's contested.** Good unscoped MCP names are squatted (`gemini-mcp`, `nano-banana-mcp`, `nano-banana-pro-mcp` all taken at 1.x), and even an *available* unscoped name can be **rejected at `npm publish` for being "too similar" to an existing package** (`gemini-image-mcp` collides with `mcp-gemini-image`) — `npm view` shows it free but publish 422s. `npm view <name> version` only proves it's unpublished, NOT publishable. Fix: **publish under the `@chrischall` scope** (`@chrischall/gemini-mcp`) — scoped names are exempt from the similarity check, same as `@chrischall/mcp-utils`. Only the npm-publish identity needs the scope: `package.json` `name` + `publishConfig.access:"public"`, `server.json` `packages[].identifier`, release-please `package-name`, and the install/`npx` commands. Keep `bin`, `mcpName`/`server.json` registry name (`io.github.chrischall/<repo>`), the `.claude-plugin` names, and the repo itself UNSCOPED so the whole identity stays one word. Decide the name (and `gh repo create`) only after `npm view` + a scope decision — renaming a repo + local dir + every manifest afterward is avoidable churn.
- **A `pass` verdict's prose nits are tracked NOWHERE — only `warn`/`fail` open the follow-up issue.** The auto-review pipeline files/updates the `Auto-review follow-ups for PR #N` issue only when the verdict is `warn` or `fail`; a `pass` whose verdict text still mentions a nit ("one nit: …") leaves it untracked, and the PR auto-merges seconds later. When a pass verdict carries prose nits, file the follow-up issue (or just fix it in a follow-up PR) yourself — nothing in the pipeline will remember it for you.
- **Re-running `pr-auto-review` does NOT re-arm; trigger a fresh PR event.** `gh run rerun` re-executes the review job but `claude-code-action` does not regenerate `structured_output` on a rerun (the "Surface verdict" step shows `skipped`), so the arm step falls back to `verdict=unknown` and won't add `ready-to-merge`. To get a clean verdict + arm, fire a fresh `pull_request` event — `gh pr close <n> && gh pr reopen <n>` (or a push) — not a workflow rerun.
- **A PR that CHANGES a workflow file can't be auto-reviewed — the Claude App's OIDC token exchange validates the workflow against `main`.** The App's app-token exchange fails `401 — "Workflow validation failed. The workflow file must exist and have identical content to the version on the repository's default branch"` whenever the PR's `pr-auto-review.yml` (or any workflow it touches) differs from the copy on the default branch. The review step then emits NO verdict (the log even says *"this is normal … you should ignore this error"*), so the PR shows `review/review → fail` / "no verdict" and never arms. This is a **chicken-and-egg every repo hits when first adopting the shared workflows** (the PR that swaps `pr-auto-review.yml` to the stub can't be reviewed by the new-but-not-yet-on-`main` workflow), and it recurs for any later workflow-only PR. Tell it apart from a real auth/token failure: the review fast-fails in ~20–30 s with the `App token exchange failed: 401 … Workflow validation failed` line, while other repos' auto-reviews still pass (so the token is fine). **Resolution: this PR must be merged ONCE outside the auto-review path** — have the human add `ready-to-merge`, which fires the deferred CI run and flips `ci-gated` to success, then auto-merge takes it (no verdict needed). Under status-mode gating the label is the ONLY route: an un-armed PR sits on `ci-gated: pending`, and a *pending* required status blocks the merge button, so the old "just squash-merge it manually" escape (which relied on a *skipped* check counting as satisfied) no longer works. After it lands on `main`, every subsequent PR auto-reviews normally. Per the never-merge rule, surface this and let the human arm/merge — don't add `ready-to-merge` yourself.
- **A green JOB does not mean the action happened — read the log, not the conclusion.** The `mcp-publish` composite *warns and skips* rather than failing when a secret is absent, so a job goes green next to `##[warning] … was NOT published`. This is the same class as "a green tag does not mean a green publish", and it fools you twice over: grepping the log for the warning text also matches the **echoed script source** (lines prefixed with the `^[[36;1m` command-echo escape), so a naive grep "finds" the warning on runs where it never fired. Grep for the real markers — `##[warning]`, `Total Upload`, `Current Version ID` — or just verify the artifact: `npm view <pkg> version`, `mcp-host get <slug>`, a live `curl`.
- **`npm view <pkg> version` is necessary but NOT sufficient — install the published tarball and run the handshake.** `npm i <pkg>@<v>` into a clean dir, then drive `initialize` + `tools/list` against its `bin`. That is what caught `manifest.json` listing 13 of the 14 tools the server registers: the tool was callable by name, the server booted fine, and nothing else reads that file — so an mcpb host would simply never have shown it. **Guard it with a test that asserts the `manifest.json` roster equals the registered roster in BOTH directions** (drive the real registrars through `createTestHarness`), and reject a blank description while you're there. Do the install in a directory with no parent `package.json`: npm walks up, and a scratch dir under one with a symlinked `node_modules` will install straight into the linked target.
- **Release-please does NOT refresh its PR for hidden commit types, so its branch goes stale and conflicts.** Merge a run of `build(deps-dev)` / `chore` / `ci` commits while a release PR is open and the release branch stays pinned at its old merge-base; because those types are `hidden: true` in `changelog-sections`, release-please sees nothing changelog-relevant and leaves the PR alone. Every run keeps reporting **success** while the PR sits `DIRTY` — the conflict is `package.json`/`package-lock.json`, which both the dep bumps and the version bump touch. `workflow_dispatch` does not fix it (same no-op logic). **Recovery: delete the release branch** (`gh api -X DELETE repos/<o>/<r>/git/refs/heads/release-please--branches--main--components--<pkg>`, which auto-closes the PR) **then re-run release-please** — it rebuilds from current `main`. The contents are generated-only, so nothing is lost. Then verify the regenerated PR's **merge-base equals `main` head** AND that it **preserved the dep bumps** — a rebuild from a stale base would silently revert every merged bump.
- **Never detect a condition by matching PROSE — export a constant or a predicate.** The recurring shape is a message whose wording serves two purposes, so a classifier keyed on it fires on the wrong one. It bit twice in one day. freshbooks regex-matched a rendered error for `FRESHBOOKS_REFRESH_TOKEN`, which is true whenever the token is merely NAMED among the missing vars — so with an app credential also missing, the message said "reconnecting cannot supply them" while the hint said "Reconnect this connector". honeybook's `classifyThrown` matched `use_magic_link` as a SYMPTOM of a rejected session, and its no-session message names `use_magic_link` as the FIX — so a user who had never connected was told their session expired. Both now key on an exported constant/predicate (`NO_AUTH_CONFIGURED`/`isNoAuthConfigured`, `CkAuthError.reason`, `HoneyBookApiError.status`) so the thrower and the reader cannot drift. A copied string keeps its own test green the day the wording changes. Corollary: when two sites must agree on a message, ONE of them owns it and the other imports it — and add a test that the real thrower actually raises it, since two strings agreeing proves nothing if nothing throws the message they agree about.
- **Mutation-test every guard, and distrust a test that passes the first time.** A test written after the fix can pass for the wrong reason. Two live examples: an assertion guarded by `if (status !== 200)` never ran because the failure it needed could not be induced (`deleteUnlessLive` returns `'failed'` rather than throwing), and a sweep test passed because the code path it targeted was skipped entirely on the tier it was exercising. Break the thing on purpose, confirm the RIGHT test fails, restore. If nothing fails, the test asserts nothing.
- **stdio transport**: logs go to **stderr only** — stdout is reserved for JSON-RPC.
- **Don't merge PRs**: open with one release-notes label; `pr-auto-review` + `auto-merge` ship it. Never add `ready-to-merge` yourself to override a warn/fail.
- **NEVER `git add -A` / `git add .` in a fleet repo — these working trees carry active uncommitted WIP.** Stage the exact paths your change touches. During a fleet-wide rollout a retry script used `git add -A` across eight repos; in `gogcli-mcp` that swept ~1,450 lines of unrelated in-progress work (new tool modules + tests + manifest edits) into a `chore:` PR that could have auto-merged. Nothing in the local flow caught it — the auto-review did, by noting the commit "bundles 20 new base tools". A script that commits must stage a whitelist and refuse when `git status --porcelain` shows anything outside it. **Recovery without touching the user's tree:** save a backup branch ref, split the bad commit (`git diff <good> <bad> -- '<your-paths>'`), rebuild in a throwaway `git worktree add --detach /tmp/x <good-sha>`, apply only your patch, commit, `push --force-with-lease` — their working copy is never checked out or reset, so the WIP stays put. Verify afterwards that the WIP files still exist and the branch diff contains only your files.
- **Auto-merge ships a PR out from under you — one complete commit, no follow-ups.** `pr-auto-review` + `auto-merge` squash-merge a PR the moment its review flips to `pass` (often < 1 min after opening). Any commit you push to the branch AFTER that lands on a now-stale branch and **orphans — it never reaches `main`** (this keeps biting: a "one more line" follow-up push silently vanishes). So open a PR only when the change is COMPLETE in a single push; never use a PR branch as a staging area for follow-ups. Left something out? Verify it actually landed (`git branch -r --contains <sha> | grep origin/main`), then it's a NEW branch + PR — not another push to the merged one. Need a real checkpoint without shipping? Open it `--draft` (auto-review skips drafts).
- **A release PR that fails CI cannot be repaired by re-running CI, and must NOT be pushed to.** If the fix lands on `main` without changing release *content*, release-please does not rebase the release branch — it sits `behind_by: 1, status: diverged`, still carrying the broken file, so every rerun fails identically. **Close it and let release-please regenerate** (`gh pr close <n> --delete-branch`, then rerun the workflow); the fresh PR comes back un-armed, carrying only `autorelease: pending`. Do **not** push the fix onto the existing release branch: it is already armed with `ready-to-merge`, so making CI green would merge, tag and publish as a side effect of a repair you thought was local. Confirm with `gh api repos/<r>/compare/main...<sha> --jq '{ahead_by,behind_by,status}'` before deciding.
- **A prior PR squash-merging out from under you leaves your follow-up branch with DUPLICATE commits — replay onto fresh `main`, don't PR the stale branch.** If you keep committing locally on `feat/X` while PR #N (off the same base) auto-merges, your branch's merge-base is now behind `main`, and `main` holds ONE squash commit while your branch still has the original individual commits of that merged work. Opening a PR from it (or pushing) re-creates a deleted branch and offers a diff full of already-merged churn. Recovery: `git fetch`; branch off current `origin/main`; replay ONLY the genuinely-new commits — `git rebase --onto origin/main <last-already-merged-sha>` (or `git checkout -b feat/X2 origin/main && git cherry-pick <last-merged-sha>..HEAD`); the cherry-picks apply cleanly because the squash's tree == the last-merged commit's tree. Then `git push origin --delete <stale-branch>` and open the PR from the clean one. (Confirms: `git log --oneline origin/main..HEAD` should show ONLY your new commits.)
- **Parallel feature PRs collide on `index.ts` + `index.test.ts`** — the tool-registrar list and the tool-count/sorted-roster are serial conflict magnets. Branch each feature off `main` (don't stack PRs — a squash-merge gives the parent a new SHA and the stacked branch then carries a duplicate of it), and expect to **rebase the second PR** after the first merges: `git reset --hard origin/main` + cherry-pick the feature commit (or `git rebase origin/main`), union-merge the two registrars, bump the count. Trivial, but it WILL conflict — don't be surprised.

## New MCP — fast path

0. **First: is a full MCP even wanted?** Default to shipping the fpx skill only (see *Deliverable: fpx skill first* above) — ASK if it wasn't dictated, CONFIRM if it was, and ship the fpx skill either way. Only continue this fast path once a full MCP is agreed.
1. **Lock the name before creating anything.** `npm view <name> version` for each candidate (and watch the similarity trap — see Gotchas); if contested, publish under `@chrischall/<name>`. Settle repo name + npm name together, THEN `gh repo create` — renaming later cascades across the repo, local dir, and every manifest.
2. Copy a same-archetype sibling's skeleton (splitwise for bearer, redfin for fetchproxy) — packaging, tsconfig, vitest from a local clone is fine, but **pull `.github/workflows/*.yml` from a freshly-updated sibling's `origin/main`, not the local tree** (see Workflows above — a stale local clone hands you the old self-contained workflows). Then do the full **Repo bootstrap** (workflows, labels incl. `release-ready`, rulesets with the `ci-gated` status check, secrets + **Claude GitHub App install**, release-please extra-files, publish scaffold, `.mcpbignore`) — it's the part that's easy to half-do. Expect the genesis push to `main` to be direct (it puts the workflows on the default branch so PRs can run); creating the **public** repo triggers an explicit auth confirmation from the user — ask before `gh repo create --public`.
3. Add `"@chrischall/mcp-utils"` (published `^x` once available; `file:../mcp-utils/<tarball>` pre-publish).
4. Write `client.ts` (deferred-config-error + one central `write()`), `tools/*.ts` (`registerTool` + `textResult`, **`confirm`-gated** writes with a dry-run `preview()`), wire `index.ts` with `runMcp`. TDD; verify endpoints from a capture before coding writes.
5. Tests with `createTestHarness` + `versionSyncTest`; mock the network. Keep them green.
6. `npm run build && npm test`. Branch + PR; let auto-merge ship it (never merge it yourself). Ship the **fpx skill** alongside (it's the minimum deliverable — never skipped, even for a full MCP).
